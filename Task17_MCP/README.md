# Task17_MCP — Orbit MCP: сервер натальных карт и гороскопов

Собственный **MCP-сервер астрологии**: не безликие гороскопы «по знакам», а
реальная астрономия (Swiss Ephemeris) поверх **натальной карты пользователя**,
дополненная живым контекстом (погода, фаза Луны, аффирмация дня). Сервер
агрегирует несколько REST-API в 23 аккуратных инструмента (16 «плоских» +
7 цепочных `elect_*`/`brief_*`) и отдает агенту
факты — трактовки делает модель.

## Архитектура

```
Агент (Task17 / Claude Desktop / любой MCP-клиент)
   │  MCP: stdio ИЛИ Streamable HTTP (/mcp)
   ▼
orbit-mcp (Go 1.26, SDK modelcontextprotocol/go-sdk)
   ├─ Astrologer-API (self-host, движок Kerykeion/Swiss Ephemeris)
   │     натальные карты, транзиты, синастрия, соляры, фаза Луны, SVG
   ├─ Open-Meteo Geocoding — «Казань» → координаты + IANA-таймзона (без ключа)
   ├─ Open-Meteo Weather   — текущая погода и прогноз дня (без ключа)
   └─ affirmations.dev     — аффирмация дня (без ключа) + перевод на русский (Google gtx)
```

Ключевой прием экономии контекста: у Astrologer-API есть **context-эндпоинты**,
возвращающие компактный XML с фактами (позиции, дома, аспекты), спроектированный
для промптов. Сервер отдает его агенту вместе с урезанным JSON (топ-аспекты по
орбису, распределение стихий/качеств) вместо сотен килобайт сырых эфемерид.

Натальные карты — **состояние сервера**: строятся один раз, сохраняются в
`orbit-charts.json` и переиспользуются всеми инструментами по имени.

## Инструменты (23)

| Tool | Что делает |
| ---- | ---------- |
| `natal_build_chart` | дата+время+город → геокодинг → таймзона → натальная карта (позиции, аспекты, стихии) + XML-контекст; сохраняется по имени |
| `transit_today` | транзиты «сейчас» к сохранённой карте (по умолчанию — последней) |
| `transit_forecast` | календарь 1–31 день: аспекты с орбисом ≤ 3° по каждому дню (self-host → цикл запросов бесплатен) |
| `synastry_compare` | совместимость двух карт: аспекты, дома партнёров, скор Discepolo с расшифровкой |
| `solar_return` | соляр на год — «прогноз от дня рождения» |
| `moon_phase` | фаза Луны, освещённость, восход/заход, ближайшие затмения |
| `vibe_today` | брифинг дня: погода + Луна + тесные транзиты + практические подсказки |
| `chart_render` | SVG-колесо карты (natal/transit/synastry, темы, язык `RU`) |
| `orbit_status` | диагностика: провайдеры + список сохранённых карт |
| `daily_affirmation` | аффирмация дня на русском (перевод Google gtx; при сбое — оригинал) + случайный волшебный смайлик |
| `journal_capture` | снимок дня в дневник: погода + Луна + тесные транзиты + аффирмация; идемпотентен за дату (для планировщика) |
| `journal_read` | сырые записи дневника за период (по умолчанию 7 дней) |
| `journal_summary` | агрегированный отчёт за период: температура, осадки, фазы Луны, частые транзиты, напоминания |
| `pulse_capture` | минутный снимок неба в SQLite: Луна + самый тесный транзит + температура; идемпотентен в пределах минуты |
| `pulse_read` | сырые снимки пульса за окно в минутах (по умолчанию 60) |
| `pulse_summary` | отчёт по пульсу: моменты смены лунного знака, таймлайн транзитов, температурная кривая |
| `elect_start` | **цепочка 1/4**: фиксирует цель, город, окно (дни) и карту; создаёт сессию `election_id`, возвращает `next` |
| `elect_scan` | **цепочка 2/4**: по каждому дню окна собирает сырые факты — тесные транзиты и фазы Луны (`candidates`) |
| `elect_score` | **цепочка 3/4**: оценивает кандидатов, отбирает топ-3 с расшифровкой очков |
| `elect_report` | **цепочка 4/4**: финальный markdown-отчёт по подбору даты |
| `brief_start` | **цепочка 1/3**: фиксирует город; создаёт сессию `brief_id`, возвращает `next` |
| `brief_collect` | **цепочка 2/3**: собирает секции брифинга (погода, Луна, транзиты, аффирмация) |
| `brief_compose` | **цепочка 3/3**: склеивает секции в готовый markdown-брифинг |

Цепочки — **state-машина на сервере**: шаг принимает идентификатор сессии,
проверяет её статус и возвращает поле `next` с именем следующего шага;
TTL сессии — 1 час. У каждого шага есть аргумент `simulate` (`"error"` /
`"empty"`) для разборов отказоустойчивости. Подробнее — раздел
[«Цепочки инструментов (state-machine)»](#цепочки-инструментов-state-machine).

## Запуск астро-движка (один раз)

Движок — open-source [Astrologer-API](https://github.com/g-battaglia/Astrologer-API)
(AGPLv3). Нужен Python 3.12+ и [uv](https://docs.astral.sh/uv/):

```sh
git clone https://github.com/g-battaglia/Astrologer-API   # ветка master = v6
cd Astrologer-API
uv run libephemeris download leb2-extended   # запас эфемерид, несколько ГБ
uv run poe start                             # поднимет http://127.0.0.1:8000
```

Проверка: `curl http://127.0.0.1:8000/health` → `{"status":"OK"}`.
Hosted-вариант через RapidAPI тоже поддерживается: задайте
`ORBIT_ASTRO_URL=https://astrologer.p.rapidapi.com` и `ORBIT_ASTRO_KEY`.

## Запуск сервера

```sh
cd Task17_MCP
go run ./app                        # MCP over stdio
go run ./app -http 127.0.0.1:5199   # MCP over Streamable HTTP + статус-страница на /
go run ./app -list                  # список инструментов
go run ./app -probe vibe_today -args '{"city":"Казань"}'   # вызов без MCP-клиента
go test ./...                       # офлайн-тесты (фейковые серверы)
```

### Подключение к чату Task17 / Task18 / Task19

Чаты Task17–Task19 подключают Orbit **по умолчанию** (в дефолтном
`AI_MCP_URLS`) и сами
поднимают его при старте через `mcpboot`, если сервер ещё не запущен — вся
цепочка стартует одной командой:

```sh
cd ../Task17
go run ./app        # чат → mcpboot поднимет orbit → orbit поднимет движок (если ORBIT_ASTRO_DIR задан)
```

Подключить Orbit вручную (например, в другом каталоге чата) можно так:

```sh
AI_MCP_URLS="orbit=http://127.0.0.1:5199/mcp" go run ./app
```

### Подключение Claude Desktop (stdio)

```json
{
  "mcpServers": {
    "orbit": { "command": "go", "args": ["run", "./app"], "cwd": "/path/to/Task17_MCP" }
  }
}
```

## Автозапуск движка

Если задан `ORBIT_ASTRO_DIR` (и `ORBIT_ASTRO_URL` — localhost), Orbit при старте
проверяет `/health` движка и, если тот не отвечает, сам запускает
`uv run poe start` в указанном каталоге (uv ищется в PATH и в `~/.local/bin`).
Логи движка — в `ORBIT_ENGINE_LOG`; поднявшись в `-probe`-режиме, движок
остаётся работать в фоне. **Остановка:** при завершении Orbit (SIGTERM/SIGINT
или штатный shutdown HTTP) движок получает SIGTERM по всей группе процессов
(uv → poe → uvicorn), при зависании — SIGKILL; «уже работавший» движок не
трогается. Для hosted-варианта (RapidAPI) автозапуск не нужен:

```sh
ORBIT_ASTRO_DIR=~/Astrologer-API make run-http   # движок + MCP одной командой
```

## Примеры диалогов

- «Построй мою карту: Анна, 21.07.1995, 14:30, Казань» → `natal_build_chart`
- «Что день грядущий мне готовит?» → `vibe_today` (погода + Луна + транзиты)
- «Когда лучше запустить проект в ближайшие две недели?» → `transit_forecast`
- «Мы с Бобом совместимы?» → `natal_build_chart` (Боб) → `synastry_compare`
- «Нарисуй нашу синастрию» → `chart_render` (type=synastry)
- «Дай аффирмацию на день» → `daily_affirmation` (оригинал + перевод)
- «Как прошла неделя по дневнику?» → `journal_summary` (агрегат за 7 дней)
- «Как менялся пульс неба за последний час?» → `pulse_summary` (смены лунного знака, таймлайн транзитов, температурная кривая)
- «Собери отчёт по пульсу неба за 24 часа» → `pulse_summary -args '{"hours":24}'`
- «Подбери благоприятную дату для запуска блога во Владимире» → `elect_start` → `elect_scan` → `elect_score` → `elect_report`
- «Собери утренний брифинг для Владимира» → `brief_start` → `brief_collect` → `brief_compose`
- «Подбери дату, но на шаге сканирования передай simulate="error"» → обрыв на `elect_scan` с внятной ошибкой и статусом сессии

## Цепочки инструментов (state-machine)

Две многошаговые цепочки, где шаги связаны через серверные сессии —
в отличие от «плоских» инструментов, каждый шаг зависит от результатов
предыдущих:

| Цепочка | Шаги (по полю `next`) | Смысл |
|---|---|---|
| Подбор даты | `elect_start` → `elect_scan` → `elect_score` → `elect_report` | цель/город/окно → транзиты по дням → оценка и топ-3 → markdown-отчёт |
| Брифинг | `brief_start` → `brief_collect` → `brief_compose` | город → секции (погода, Луна, транзиты, аффирмация) → готовый брифинг |

**Гарантии предсказуемости** (требование задания Task19):

- **Агент не выдаёт результат, которого нет** — `elect_report`/`brief_compose`
  строят текст только из реально собранных и оценённых данных;
- **Агент не вызывает следующий инструмент на пустых данных** — guard'ы
  отклоняют шаг: `elect_score` на пустом сканировании («кандидатов нет —
  сканирование вернуло 0 дней»), `brief_compose` на несобранной сессии
  («секции брифинга не собраны — вызовите brief_collect»), любой шаг вне
  порядка («данные не собраны (статус started) — сначала brief_collect»);
- **Понятно, на каком шаге остановились и почему** — ошибки называют шаг
  и причину, поле `status` сессии видно через `orbit_status`.

Механика: сессии живут **1 час** (`electTTL`/`briefTTL`); поле `next`
подсказывает модели следующий шаг; аргумент `simulate` (`"error"` — шаг
вернёт ошибку, `"empty"` — пустой результат) служит для разборов
отказоустойчивости. Тесты — `orbit/chain_test.go`: happy path, ошибка на
шаге 2, пустой результат на шаге 1, вызов вне порядка, истечение TTL.

## Дневник наблюдений и планировщик

`journal_capture` собирает суточный снимок (погода, фаза Луны, тесные
транзиты к последней карте, аффирмация) и пишет его в
`orbit-journal.json` — одна запись на дату, повторный вызов перезаписывает.
Записи накапливаются, а `journal_summary` превращает их в агрегированный
отчёт за период: средняя/мин/макс температура, дни с осадками, траектория
фаз Луны, самые частые транзиты и детерминированные напоминания
(«осадки вероятны в 4 из 7 дней», «перепад температур 12 °C»).

Планировщик дёргает MCP-инструменты по расписанию — собирать данные раз в
день и раз в неделю строить отчёт:

> **В связке с чатом Task18** планировщик встроен в само приложение: задача
> «Дневник — снимок дня» (`21:00`) вызывает `journal_capture` как
> MCP-инструмент — прямой вызов (поле `tool`, без модели) кладёт сырой JSON
> в журнал запусков, задача с промптом возвращает готовый текст. Cron ниже —
> для автономного запуска сервера без чата.

```cron
# ежесуточный снимок в 08:00
0 8 * * * cd /Users/milkinatatyana/ai-chat-go/Task17_MCP && go run ./app -probe journal_capture >> bin/journal.log 2>&1
# агрегированный отчёт по понедельникам в 09:30
30 9 * * 1 cd /Users/milkinatatyana/ai-chat-go/Task17_MCP && go run ./app -probe journal_summary -args '{"days":7}' >> bin/journal-summary.log 2>&1
```

На macOS то же самое умеет launchd (LaunchAgent с `StartCalendarInterval`).
Ручная проверка без планировщика: `make probe-journal-capture`,
`make probe-journal-summary`. Сырые записи в любой момент:
`journal_read` (например `-args '{"days":14}'`).

## Пульс неба и частый опрос (SQLite)

`pulse_capture` — лёгкий минутный снимок (фаза Луны и знак, самый тесный
транзит, температура) в SQLite-базу `orbit-pulse.db` (pure-Go драйвер,
WAL). Ключ записи — минута, повтор в ту же минуту перезаписывает её, так
что частые вызовы безопасны. Ценность поминутных данных — в событиях:
`pulse_summary` показывает, **когда** Луна сменила знак, когда транзит
вошёл в орбис и ушёл из него, и температурную кривую за окно.

```cron
# пульс каждую минуту (retention 30 дней чистится автоматически)
* * * * * cd /Users/milkinatatyana/ai-chat-go/Task17_MCP && go run ./app -probe pulse_capture >> bin/pulse.log 2>&1
# отчёт за сутки — каждый день в 09:00
0 9 * * * cd /Users/milkinatatyana/ai-chat-go/Task17_MCP && go run ./app -probe pulse_summary -args '{"hours":24}' >> bin/pulse-summary.log 2>&1
```

> В чате Task18 то же самое делает встроенный планировщик: «Пульс — снимок»
> (`@every 1m`) — **прямой вызов** `pulse_capture` (поле `tool`, ~20 мс,
> 0 токенов), «Пульс — итог дня» (`21:00`) — агентский ход с промптом,
> возвращающий оформленный отчёт.

Для launchd — `StartInterval` 60. Ручные проверки: `make probe-pulse-capture`,
`make probe-pulse-summary`; сырые снимки — `pulse_read` (например
`-args '{"minutes":120}'`). Отличие от дневника: journal — суточные
«дневниковые» записи с аффирмацией, pulse — поминутная хронология неба.

## Отрисовка карт (chart_render)

`chart_render` возвращает результат из двух частей:

- **Модель видит только компактную сводку** (`type`, `chart`, `second`, `bytes`,
  `note`) — ни SVG, ни путей, ни ссылок, чтобы они не попадали в сообщения чата;
- **SVG едет отдельным image-контентом MCP** (`image/svg+xml`): клиент чата
  сохраняет картинку в кэш и показывает её **прямо в сообщении** (чата Task17
  раздаёт каталог картинок по `GET /files/<имя>` и дописывает ссылку в конец
  ответа — фронтенд рендерит колесо инлайновой картинкой).

Дополнительно (для просмотра вручную):

- файл-галерея в `ORBIT_CHARTS_DIR` (`anna-natal.svg`, `anna-synastry-bob.svg` —
  имя детерминировано, повторный рендер перезаписывает файл);
- в HTTP-режиме — `http://127.0.0.1:5199/charts/anna-natal.svg` (только `.svg`,
  прочие файлы наружу не отдаются);
- галерея всех рендеров — на статус-странице `http://127.0.0.1:5199/`.

## Ограничения

- Первый запрос к движку после старта может считаться медленно (инициализация эфемерид) — таймаут `30s` рассчитан с запасом.
- `ORBIT_ASTRO_KEY` не задан → запросы без авторизации, что верно только для self-host.
- Данные рождения остаются на вашей машине — это осознанное преимущество self-host.
