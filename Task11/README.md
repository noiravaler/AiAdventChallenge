# ai-chat-go — Task11

Чат с ИИ через OpenAI-совместимый API с веб-интерфейсом в стиле плоского
мессенджера (бирюзовая тема). Написан на Go без внешних зависимостей: только
стандартная библиотека.

> Task11 — чат с **инструментами**, **Markdown**, **сохранением контекста в
> SQLite**, **проверкой ожидаемых ответов викторины** (зелёная/красная плашка
> после сверки ответа модели с ожидаемым), **сжатием контекста на лету**
> (три стратегии: Summary, Sliding Window, Sticky Facts), **прогоном
> сценария через модель** (чип «Проверка памяти»: каждая реплика — отдельный
> запрос, ответ модели — реальный, без заглушек и подмены),
> **пошаговым логом** с вложенными шагами и **ветвлением диалога**
> (альтернативные продолжения в стиле ChatGPT с переключателем «⟨ 1/2 ⟩»),
> и главное — **трёхслойной памятью** (краткосрочной, рабочей,
> долговременной; см. «Память: три слоя»).

## Возможности

- Веб-чат в браузере: локальный сервер + страница-мессенджер (бирюзовая тема).
- Потоковый вывод (SSE) прямо в окно чата.
- Поддержка reasoning-моделей: трейс `reasoning`/`reasoning_content`
  не показывается, но считается «активностью» и не даёт оборвать долго
  думающую модель.
- История диалога на сервере; кнопка «Новый диалог» (очистка истории).
- **Список моделей обновляется автоматически** при загрузке страницы из
  `GET {AI_BASE_URL}/models`; не-чат модели (embeddings/reranker/whisper)
  отфильтровываются по имени. Если API недоступен — фолбэк на `AI_MODELS`
  или `DefaultModels`.
- **Резервный провайдер `[reserve]`**: независимый OpenAI-совместимый эндпоинт
  (по умолчанию OpenCode Zen / DeepSeek), отдельный от основного GPUStack.
  Включается, когда основной недоступен; в сайдбаре отображается пунктирным
  контактом.
- **Управление форматом ответа** из интерфейса: `text`, `json`, `jsonschema`,
  `jsonschema_structured` (strict), плюс `stop`-последовательность.
- Панель **«Детали»** (`GET /api/debug`) с блоками:
  - **«Запрос»** — JSON последнего **чат-обмена** (запросы сжатия и проверки
    его не перезатирают);
  - **«Шаги»** — лог за весь диалог; каждый шаг «Раунд N» показывает токены
    своего API-вызова («Токены: запрос X · ответ Y»); вложенные шаги
    (инструменты, сжатие контекста, проверка ожидаемого ответа) рисуются
    внутри породившего их шага с отступом;
  - **«Количество токенов»** — «Токены запроса» (последний обмен), «Токены
    ответа», «Токены истории диалога» (с подсказкой по наведению на ⓘ) и
    «Время»;
  - **«Сжатие»** — после сжатия контекста: стратегия, сколько сообщений
    сжато, токены вызова и результат с Markdown-форматированием — сводка
    (Summary) или блок фактов «ключ: значение» (Sticky Facts). Блок «Шаги»
    при этом свёрнут по умолчанию;
  - **«Ошибка»** — диагностика последней ошибки (ошибка API, «нет ответа»,
    превышение лимита токенов, нарушение JSON-схемы, некорректный/слишком
    большой запрос). Показывается только после реальной ошибки в текущей
    сессии; при загрузке страницы и смене модели не поднимается из старого
    состояния сервера.
- Ползунки **`max_tokens`** («Ответ модели», блок свёрнут по умолчанию),
  допустимого **таймаута ответа** (5–30 с) в интерфейсе.
- **Вопросы «+» слева от поля ввода**: всплывающее меню со списком вопросов из
  тестового файла викторины (`testdata/quizzes/memory-quiz.txt`,
  `GET /api/quiz`). Выбранный вопрос отправляется как обычное сообщение, а под
  ответом модели показывается пометка «Ожидаемый ответ» — она видна только в
  интерфейсе: сам ответ в модель не отправляется и в контексте общения не
  учитывается. Ответ модели сверяется с ожидаемым отдельным запросом
  (`POST /api/validate`): плашка становится зелёной (совпадает) или красной
  (не совпадает). Меню закрывается кликом вне его и по Escape.
- **Понятные ошибки больших запросов**: тело `POST /api/chat` принимается до
  64 МБ (большая вставка JSON-экранируется и вырастает в несколько раз); при
  превышении — «Сообщение слишком большое», при невалидном JSON — причина
  разбора; обе ошибки попадают и в чат, и в блок «Ошибка» «Деталей».
- Терминальный режим (`-cli`) и разовый запрос из командной строки.
- Системный промпт, смена модели, настройка лимита токенов и таймаута.
- Конфигурация через переменные окружения, файл `.env` или флаги.
- **Инструменты агента (function calling)** доступны модели в чате:
  `get_current_time(region)` — текущие дата/время в заданном регионе (IANA);
  `roll_dice()` — случайное целое от 1 до 6 (именно игральный кубик; для
  подбрасывания монеты модель отвечает случайно, без инструмента). Модель сама
  решает, когда их звать; выполнение и подстановка результата происходят
  автоматически, невидимо для пользователя.
- **Markdown-форматирование** сообщений: заголовки, маркированные/нумерованные
  списки, жирный/курсив/зачёркнутый, код (строчный и блочный), ссылки, цитаты.
- **Ползунок «Максимальное количество циклов»** (1–10, по умолчанию 6): сколько
  раундов модель может запрашивать инструменты (в одном раунде их может быть
  несколько — лимит на число раундов, а не на число вызовов). Блок свёрнут
  по умолчанию.
- **Ползунки «Размер контекста»** в блоке настроек после таймаута — их два:
  **«Порог контекста»** (5–40, по умолчанию **10**) — число сообщений, при
  превышении которого вызывается сжатие, и **«Количество сообщений»** (3–30,
  по умолчанию **5**) — число последних сообщений, до которых выполняется
  сжатие (которые остаются как есть). Изменение применяется сразу:
  `POST /api/compress`, и если новое «Количество сообщений» меньше текущего
  числа сообщений — диалог сворачивается до окна немедленно, не дожидаясь
  порога. Таймаут ответа по умолчанию — **20 с**.
- **Блоб-сценарий «Проверка памяти»** над строкой ввода: клик запускает
  **прогон сценария через модель** (`POST /api/dialog/run`) — каждая реплика
  из файла сценария (`memory-check.txt` — 10 пользовательских реплик,
  ответы модели в файле не хранятся) отправляется отдельным запросом к
  модели, прогон **дожидается реального ответа**, который стримится в чат
  посимвольно и сохраняется как есть; только потом уходит следующая
  реплика. Пустой ответ модели не оставляет реплику без ответа: прогон
  повторяет запрос (до двух попыток, с удвоенным лимитом токенов —
  reasoning-модели могут израсходовать весь бюджет размышлениями) и
  останавливается с ошибкой, если ответа нет и после них. Перед сжатием,
  вызывающим модель, в чат выводится статус «Сжимаю контекст…» — пауза
  после ответа видна, а не выглядит зависанием. Плашка свёрнутого
  контекста рисуется на месте, сам лог во время прогона не
  перерисовывается (полная перерисовка из истории — по завершении
  прогона), поэтому идущие реплики не пропадают. Токены, память и шаги
  обновляются в панелях на лету. Прогон
  **продолжает активную ветку** — дерево
  ветвлений и выполненные сжатия сохраняются (сжатие по ходу прогона
  происходит только в текущей ветке); начать с чистого листа можно кнопкой
  «Очистить диалог». Прогон стримится событиями NDJSON; сжатие контекста
  работает на
  лету. Во время прогона плашка превращается в кнопку **«Остановить»**:
  повторный клик прерывает прогон — завершённые реплики сохраняются, в чат
  выводится информационное сообщение **«Сценарий остановлен»**. Ошибка
  обращения к модели прерывает прогон и попадает в блок «Ошибка» панели
  «Детали».
- **Сжатие контекста на лету**: как только сообщений становится больше
  «Порога контекста», старые сворачиваются выбранной стратегией — без
  каких-либо действий пользователя. На месте свёрнутых сообщений в чате
  стоит приглушённая плашка «Сжатый контекст · показать сводку» (клик
  разворачивает Markdown-сводку); результат хранится в
  истории (переживает перезапуск); сводка уходит модели как системное
  сообщение, факты — первым сообщением каждого запроса. В панели «Детали»
  появляется блок «Сжатие»: стратегия, сколько сжато, токены вызова и
  результат. Стратегии — см. раздел «Сжатие контекста» ниже.
- **Блок «Стратегия сжатия»** в панели настроек: тоггл «Сжимать
  контекст» (вкл/выкл) и радиокнопки **Summary**, **Sliding
  Window**, **Sticky Facts** — описание каждого варианта вынесено в подсказку
  «i» рядом с названием; по умолчанию Summary. Настройки применяются с каждым
  запросом **и сразу при изменении** (`POST /api/compress`): если диалог уже
  больше нового порога, сжатие выполняется немедленно, не дожидаясь следующего
  сообщения.
- **Кнопка удаления диалога** (корзина в шапке) открывает контекстное меню с
  тремя уровнями очистки:
  **«Удалить чат»** — стирает сообщения и краткосрочный слой (рабочая память —
  задача, заметки, факты — сохраняется);
  **«Удалить историю»** — очищает краткосрочную и рабочую память (сообщения,
  задача, заметки, факты), долговременная остаётся;
  **«Удалить все»** — очищает все уровни памяти: чат, краткосрочный, рабочий и
  долговременный (все модели; с подтверждением).
- **Панель «Память»** (в правой панели): три блока по слоям — краткосрочный,
  рабочий, долговременный — с текущим содержимым каждого, **объёмом слоя в
  токенах** в заголовке (краткосрочный — фактический размер контекста ветки;
  рабочий и долговременный — оценка ~4 байта/токен) и **тумблером включения
  у каждого блока** (по умолчанию все включены): выключенный слой
  игнорируется — его данные не попадают в промпт, как будто слоя нет, но
  физически не удаляются; тумблер обратно возвращает слой в работу.
  Переключение уходит на `POST /api/memory/layers`.
- **Ветвление диалога**: альтернативные продолжения в стиле ChatGPT — кнопка
  «Ветвление отсюда» на сообщении пользователя, «Переспросить» на ответе
  модели и переключатель «⟨ 1/2 ⟩» — один на каждое ветвление (у версий
  ответа — под ответом модели, у ветвления — под сообщением, от которого
  ответвились); сжатие
  контекста ведётся отдельно для каждой ветки и сворачивает только её
  собственные сообщения — всё, что до точки ветвления, остаётся видимым.
  См. «Ветвление диалога» ниже.
- **Сохранение контекста и памяти между перезапусками**: история, выбранная
  модель, размер истории (токены), счётчик `total_prompt_tokens`, состояние
  веток и долговременная память записываются в базу SQLite
  `history/chat.db` (путь настраивается `AI_DB_FILE`) и восстанавливаются
  при запуске. Старые JSON-файлы мигрируются автоматически. См.
  «Сохранение контекста» и «Память: три слоя» ниже.

- Go 1.22 или новее.

## Настройка

| Переменная | По умолчанию | Описание |
|---|---|---|
| `AI_API_KEY` | — | API-ключ. Не нужен для локального сервера. |
| `AI_BASE_URL` | `https://api.openai.com/v1` | Базовый URL API (без `/chat/completions`). |
| `AI_MODEL` | `gpt-4o-mini` | Имя основной модели. |
| `AI_MODELS` | `DefaultModels` | Явный список моделей для бокового меню (фолбэк). |
| `AI_SYSTEM` | — | Системный промпт. |
| `AI_TIMEOUT` | `5m` | Таймаут одного запроса, например `90s`. |
| `AI_MAX_TOKENS` | `0` | Максимум токенов ответа, `0` — на усмотрение провайдера. |
| `AI_RESERVE_BASE_URL` | `https://opencode.ai/zen/v1` | Базовый URL резервного провайдера `[reserve]`. |
| `AI_RESERVE_API_KEY` | — | Ключ резервного провайдера (нужен, если endpoint не локальный). |
| `AI_RESERVE_MODEL` | `glm-5.3-flash-free` | Модель резервного провайдера `[reserve]`. |
| `AI_DB_FILE` | `history/chat.db` | Путь к базе SQLite: диалог, рабочее состояние веток и долговременная память (см. «Память: три слоя»). Пустое значение отключает сохранение. |
| `AI_HISTORY_FILE` | `history/.chat-history.json` | Устаревший базовый путь к JSON-истории: существующие файлы мигрируются в SQLite при первом запуске, новые не создаются. |

Переменные окружения имеют приоритет над `.env`, флаги — над обоими.

| Провайдер | `AI_BASE_URL` | `AI_MODEL` (пример) |

Для локальных серверов ключ можно не указывать.

## Использование

```sh
go run ./app                            # веб-чат: сервер + браузер
go run ./app -cli                       # чат в терминале
go run ./app "Объясни, что такое горутина"
go run ./app -model gpt-4o "Скажи что-нибудь"
go run ./app -no-stream "Ответь одним абзацем"
go run ./app -system "Отвечай только по-русски"
```

### Веб-интерфейс

При запуске без аргументов клиент поднимает сервер на `http://127.0.0.1:5190`
и открывает его в браузере (бирюзовый мессенджер с пузырями сообщений). Если
порт занят, берётся следующий свободный. Сервер слушает только `127.0.0.1`,
переписка не покидает компьютер. Страница умеет:

- отправлять сообщения (Enter или кнопка с бумажным самолётиком);
- показывать ответ по мере поступления токенов (включая трейс reasoning), с
  **Markdown-разметкой**;
- отправлять сообщения кликом по **блобу** над строкой ввода (сценарий
  «Проверка памяти»);
- отправлять **вопросы викторины** через меню кнопки **«+»** слева от поля
  ввода (с пометкой ожидаемого ответа под сообщением);
- «Новый диалог» (кнопка «+» в шапке) — очистить историю на сервере;
- **ветвить диалог**: «Ветвление отсюда» на сообщении пользователя,
  «Переспросить» на ответе модели, переключатель «⟨ 1/2 ⟩» — один на каждое
  ветвление;
- выбирать модель в боковом меню; список обновляется из `/api/models`, для
  основной и резервной модели;
- настраивать `max_tokens` (ползунок), таймаут ответа (5–30 с) и **максимальное
  количество циклов** (ползунок 1–10);
- выбирать формат ответа (`text` / `json` / `jsonschema` /
  `jsonschema_structured`) и задавать `stop`-последовательность;
- смотреть «Детали» (запрос/ответ, пошаговый лог «Шаги» с токенами раундов,
  «Количество токенов», время и диагностика) через `GET /api/debug`;
- после перезагрузки страницы история восстанавливается (`GET /api/history`)
  целиком вместе с активной веткой; показывается активная ветка, остальные
  версии доступны через переключатели «⟨ 1/2 ⟩».

Чтобы браузер не открывался автоматически, добавьте `-no-open`.

### Флаги

| Флаг | Описание |
|---|---|
| `-base-url` | Базовый URL API. |
| `-api-key` | API-ключ (лучше через `AI_API_KEY`, чтобы ключ не попал в историю команд). |
| `-model` | Имя модели. |
| `-system` | Системный промпт. |
| `-max-tokens` | Максимум токенов ответа. |
| `-timeout` | Таймаут запроса, например `2m`. |
| `-no-stream` | Не использовать потоковый вывод. |
| `-web` | Веб-интерфейс с открытием в браузере (по умолчанию `true`). |
| `-cli` | Терминальный чат вместо веб-страницы. |
| `-port` | Порт веб-интерфейса (по умолчанию `5190`). |
| `-no-open` | Не открывать браузер автоматически. |

`ai-chat -h` покажет справку.

### Команды в терминальном режиме (`-cli`)

| Команда | Действие |
|---|---|
| `/help` | Показать справку. |
| `/reset` | Очистить историю диалога. |
| `/model` | Показать текущую модель. |
| `/model <имя>` | Переключить модель. |
| `/system` | Показать системный промпт. |
| `/system <текст>` | Задать системный промпт и очистить историю. |
| `/exit`, `/quit` | Выйти. |

## Как это работает

Клиент отправляет `POST {AI_BASE_URL}/chat/completions` с заголовком
`Authorization: Bearer <AI_API_KEY>` и телом в формате OpenAI Chat Completions.
В потоковом режиме ответ читается как Server-Sent Events: строки `data: {...}`
разбираются, из `choices[].delta.content` собирается текст, `data: [DONE]`
завершает поток. Токены `choices[].delta.reasoning_content`/`reasoning`
(трейс думающей модели) не показываются, но регистрируются как активность,
чтобы не оборвать генерацию.

Веб-интерфейс работает так: браузер шлёт `POST /api/chat` с JSON
`{"message": "...", "format": ..., "maxTokens": ..., "timeout": ...,
"schema": ..., "stop": ..., "compress": {...}}`, сервер вызывает API и
пересылает токены ответа в тело HTTP-ответа по мере поступления; страница
читает поток через `ReadableStream` и дорисовывает текст в реальном времени.
Блок `compress` задаёт настройки сжатия: `{"enabled": bool,
"strategy": "summary"|"sliding"|"sticky", "keep": N}` — сервер применяет их
на лету после каждого обмена. История хранится на сервере в виде дерева
сообщений и отдаётся через `GET /api/history` (каждое сообщение с `id` и
`alts`, плюс `active` — см. «Ветвление диалога» ниже); кроме того, она
сохраняется на диск между перезапусками — см. «Сохранение контекста» ниже.

Список моделей для сайдбара берётся из `GET {AI_BASE_URL}/models` и
фильтруется по имени (отбрасываются embedding/rerank/whisper/tts/audio/asr).
Если основной endpoint недоступен, используется резервный `[reserve]`, а для
фолбэка списка — `AI_MODELS`/`DefaultModels`.

Диагностика доступна через `GET /api/debug` и возвращает детали для панели
«Детали»: последний чат-запрос/ответ (сжатие и проверка его не перезатирают),
причину приостановки (ошибка API, «нет ответа», превышение лимита токенов,
нарушение JSON-схемы), лог `steps` за весь диалог (раунды — со своими
`prompt_tokens`/`completion_tokens`, инструменты/сжатие/проверка — во
вложенных `sub`-шагах), суммарные `tokens`, `prompt_tokens`,
`completion_tokens`, `history_tokens`, накопительные `total_prompt_tokens`,
счётчик сжатий `compress_seq`, текущий блок `facts` и последнее сжатие
`last_compress`.

Проверка ответа викторины: `POST /api/validate` с `{"answer", "expected"}` —
модель оценивает совпадение (JSON-ответ), сервер возвращает `{"correct",
"comment"}`; токены вызова в счётчики не входят, вызов попадает в «Шаги»
вложенным шагом «Проверка ожидаемого ответа: верно/неверно».


## Вопросы «+» (викторина)

Кнопка **«+»** слева от поля ввода открывает меню с вопросами тестовой
викторины (`testdata/quizzes/memory-quiz.txt`, вшита через `go:embed` в
`testassets.go`, отдаётся через `GET /api/quiz`):

| Пункт меню | Источник | Endpoint |
|---|---|---|
| Вопросы викторины «Проверка памяти» (6 шт.) | `testdata/quizzes/memory-quiz.txt` (вшит через `go:embed` в `testassets.go`) | `GET /api/quiz` |

Выбранный вопрос отправляется как обычное сообщение; под ним появляется
пометка «Ожидаемый ответ» из того же файла — она не отправляется модели и в
контексте не учитывается.

### Проверка ожидаемого ответа

После ответа модели на вопрос викторины клиент отправляет `POST
/api/validate` с ответом модели и ожидаемым текстом. Сервер отдельным
запросом к модели (с JSON-форматом и тем же ключом) выясняет, совпадает ли
смысл ответа с ожидаемым, и возвращает `{"correct": true|false, "comment":
"..."}`. Плашка «Ожидаемый ответ» в чате окрашивается: зелёная — ответ
засчитан, красная — нет. Плашка привязана к конкретному ответу модели:
при перерисовке истории (в том числе при переключении веток) она
восстанавливается у своего ответа и не «переезжает» на ответ в другой ветке;
вызов валидации виден в «Шагах» вложенным шагом.

## Сжатие контекста

Когда сообщений в диалоге становится больше «Порога контекста» (ползунок
5–40, по умолчанию 10), контекст сжимается **автоматически, на лету** — без
каких-либо действий пользователя — до «Количества сообщений» (ползунок 3–30,
по умолчанию 5): столько последних сообщений остаётся как есть. Если
сообщений не больше порога (или порог не превышает «Количество сообщений»),
сжатие не вызывается — кроме случая, когда пользователь сам уменьшает
«Количество сообщений»: тогда диалог сворачивается до нового окна сразу
(применение настроек сжимает принудительно). Стратегия выбирается в панели настроек
(блок «Стратегия сжатия»):

| Стратегия | Как работает | Что видит модель | Плашка в чате |
|---|---|---|---|
| **Summary** (по умолчанию) | Модель составляет краткую сводку по удаляемой переписке | Сводка как системное сообщение + последние N сообщений | «Контекст сжат: …» |
| **Sliding Window** | Старые сообщения просто удаляются, без вызова модели | Только последние N сообщений | «Сжатие контекста (Sliding Window): …» |
| **Sticky Facts** | Модель ведёт блок фактов «ключ: значение»: при сжатии обновляет его по удаляемой переписке | Последние N сообщений + блок фактов первым сообщением | «Сжатие контекста (Sticky Facts): …» |

Детали:

- Настройки сжимаются в блок `compress` тела `/api/chat` и `/api/dialog/run`
  и применяются на лету после каждого обмена.
- В ветке сжимаются только её собственные сообщения: префикс до точки
  ветвления и сама точка остаются видимыми (см. «Ветвление диалога» ниже).
- Факт сжатия хранится в истории: роль `summary` (сводка, уходит модели) или
  `marker` (служебная запись для интерфейса, модели не отправляется). В чате
  на этом месте стоит заметная сворачиваемая плашка «Сжатый контекст ·
  показать сводку» — свёрнутая часть диалога не выглядит пропавшей, что
  особенно заметно в ветках (при переключении ветки история
  перерисовывается целиком). Если сжатие скрыло точку ветвления, её
  переключатель «⟨ 1/2 ⟩» переезжает на эту плашку.
- Блок «Сжатие» в «Деталях» показывает стратегию, число сжатых сообщений,
  токены вызова и результат (сводку или факты) с Markdown-форматированием.
- Каждое сжатие попадает в «Шаги» вложенным шагом («Сжатие контекста
  (Summary)…» и т.п.).
- Ручной кнопки сжатия нет: сжатие происходит само по достижении порога,
  а изменение настроек сжатия в панели применяется сразу (`POST /api/compress`).

## Ветвление диалога

История чата хранится как дерево сообщений (у каждого `id` и ссылка на
родителя `parent`), а не линейный список. Это позволяет вести несколько
альтернативных продолжений одного диалога — как в ChatGPT — и переключаться
между ними, не теряя ни одну из веток.

Интерфейс:

- **«Ветвление отсюда»** — иконка на сообщении пользователя: всё, что было
  после этого сообщения, остаётся на прежней ветке, а новые сообщения пойдут
  в новую (`POST /api/branch` с `{"after": id}`); новая ветка сразу
  становится активной.
- **«Переспросить»** — иконка на ответе модели: то же ветвление от вопроса,
  плюс сразу отправляется повторный запрос (`POST /api/chat` с
  `"regenerate": true`) — прежний ответ остаётся доступным через
  переключатель.
- **Переключатель «⟨ 1/2 ⟩»** — один на каждое ветвление (их может быть
  несколько в разных местах диалога). Пилюля появляется под сообщением,
  к которому относится ветвление: у «версий ответа» (переспрос) — под
  активным ответом модели — даже если этот ответ пустой (пустые версии
  тоже считаются) и даже если у того же вопроса есть и альтернативная
  вопросная ветка (её лист остаётся в списке переключателя); у ветвления
  от сообщения пользователя — под этим сообщением (справа; под ответом
  модели — слева). Пустой ответ модели отображается приглушённой
  курсивной пометкой «пустой ответ модели», а не пропадает; обычный чат
  при пустом ответе тоже повторяет запрос (до двух попыток с удвоенным
  лимитом токенов). Стрелки переключают ветки
  без обращения к модели (история просто перерисовывается), счётчик
  показывает позицию активной ветки. Ветки восстанавливаются и после
  перезапуска приложения. Пустая форк-ветка («Ветвление отсюда», от которой
  ещё не ушли новым сообщением) остаётся в переключателе и после ухода с
  неё; если точка ветвления скрыта сжатием, её переключатель переносится на
  плашку «Сжатый контекст», поэтому дерево ветвей не пропадает.

Детали:

- Видимая история — путь по дереву от корня до активного листа; сообщения
  других веток в контекст модели не попадают.
- **Сжатие контекста ведётся отдельно для каждой ветки**: сводка/факты и
  граница сжатого префикса хранятся у листа ветки, поэтому переключение
  между ветками не портит уже выполненное сжатие, а продолжения в разных
  ветках сжимаются независимо.
- **Сжатие в ветке сворачивает только её собственные сообщения** — те, что
  появились после точки ветвления. Общий префикс (сообщения до ветвления) и
  сама точка ветвления остаются видимыми: унаследованная на момент форка
  сводка фиксируется «замороженной» плашкой, общий хвост и точка ветвления
  показываются как есть, затем идёт сводка самой ветки и её хвост. Вложенный
  форк наследует все замороженные стадии родительской ветки. Ветка,
  созданная до этого изменения, при загрузке восстанавливает точку
  ветвления автоматически.
- Во время генерации ответа и прогона сценария операции с ветками
  возвращают `409 Conflict` — ветви можно менять только между обменами.
- `DELETE /api/branch` удаляет ветку вместе с её уникальными сообщениями;
  активную ветку удалить нельзя (`409`).

API ветвления:

| Endpoint | Описание |
|---|---|
| `POST /api/branch` | `{"after": id}` — создать ветку после сообщения `id`. |
| `POST /api/branch/switch` | `{"id": id}` — переключиться на ветку с листом `id` (без вызова модели). |
| `GET /api/branches` | Список веток: `id` листа, заголовок, число сообщений, признак `active`. |
| `DELETE /api/branch` | `{"id": id}` — удалить ветку (активную нельзя — `409`). |
| `GET /api/history` | Помимо `messages` возвращает `active`; каждое сообщение несёт `id` и `alts` (список листьев-альтернатив, когда их больше одной). |
| `POST /api/chat` | Флаг `"regenerate": true` — переспросить текущий вопрос заново, не добавляя сообщение пользователя. |

Если сообщение слишком большое (тело `POST /api/chat` больше 64 МБ) или не
разбирается как JSON, сервер возвращает понятную русскоязычную ошибку и
заполняет блок «Ошибка» в панели «Детали».

## Сохранение контекста (истории)

Веб-чат сохраняет диалог между перезапусками, чтобы после остановки и запуска
приложение продолжило беседу с того места, где остановились. Начиная с этой
версии контекст хранится в **SQLite** (`modernc.org/sqlite`, pure Go, без cgo):
одна база на все модели, путь задаётся переменной `AI_DB_FILE` (по умолчанию
`history/chat.db`). Старые JSON-файлы (`history/.chat-history-<модель>.json`)
мигрируются в базу автоматически при первом запуске и помечаются
`*.migrated` — ничего не теряется. Пустой `AI_DB_FILE` отключает сохранение.

База устроена по слоям памяти (см. следующий раздел): у диалога, рабочего
состояния веток и долговременной памяти — отдельные таблицы.

- **Таблицы** — `messages` (дерево сообщений: `id`/`parent`, роль, текст,
  `tool_calls`, время), `branches` (состояние каждой ветки: CoveredUpTo,
  сводка, блок фактов, задача, заметки, токены), `session_state` (активная
  ветка, `next_id`, счётчики токенов, переключаемые листья) и `memories`
  (долговременная память). Системный промпт не сохраняется и пересоздаётся
  из текущей конфигурации при запуске.
- **Когда пишется** — после каждого изменения истории: завершённого обмена
  репликами, новой модели, ветвления/переключения веток. Запись идёт одной
  транзакцией (`storage.SaveSession`). Если запрос к модели завершился
  ошибкой, незавершённый ход пользователя отбрасывается и это состояние тоже
  сохраняется.
- **Когда читается** — при старте сервера (`server.New` → `restore`): активной
  становится модель с самой свежей репликой (`LatestSessionModel`), дерево
  восстанавливается целиком, включая ветки.
- **Без очистки по сроку давности** — история не удаляется автоматически и
  живёт до тех пор, пока пользователь не очистит её корзиной. «Удалить чат»
  чистит диалог и краткосрочный слой, но сохраняет рабочее состояние ветки и
  **не трогает долговременную память**; «Удалить историю» стирает ещё и
  рабочую; «Удалить все» стирает и долговременную (все модели). Папка
  `history/` исключена из git.

## Память: три слоя

Информация диалога разделена на три типа памяти. Слои хранятся отдельно,
наполнение каждого — явное, и для каждого слоя определено правило, что именно
попадает в промпт.

| Слой | Что хранит | Где хранится | Что идёт в промпт |
|---|---|---|---|
| **Краткосрочная** | текущий диалог | таблица `messages` (дерево с ветками) | последние `keep` сообщений активной ветки дословно (окно автосжатия) |

Объём краткосрочного слоя в панели «Память»: реальный размер контекста
последнего запроса; сразу после сжатия (счётчик ветки обнуляется) —
приблизительная оценка по фактическому содержимому пути, поэтому значение
не падает до нуля.

Факты (`facts`) заполняются при обоих сжатиях: Sticky Facts переписывает
блок целиком, Summary добавляет строки «ФАКТ: ключ: значение» из конца
сводки (дедуп по строке, блок ограничен 15 последними фактами) — и в обоих
случаях факты переносятся в долговременную память.
| **Рабочая** | данные текущей задачи | таблица `branches`: задача (`task`), заметки (`notes`), сводка (`summary`), факты (`facts`) | блок «Рабочая память текущей задачи» (задача + заметки) и «Блок важных фактов» — всегда, одной system-строкой |
| **Долговременная** | профиль, решения, знания | таблица `memories` (по модели) | профиль — всегда (до 10 строк); решения и знания — при совпадении темы вопроса, бюджет ~600 токенов |

Как наполняется долговременная память (явная маршрутизация записи):

1. **Факты сжатия — основной канал.** При сжатии Sticky Facts модель ведёт
   блок «ключ: значение» и возвращает цель задачи (`ЗАДАЧА:`) и факты с тегами
   (`[профиль]`, `[решение]`, `[знание]`). Каждая строка факта дедуплицируется
   по ключу и попадает в таблицу `memories`. Факт, подтверждённый двумя
   сжатиями подряд (`confirmations ≥ 2`), становится «долговременным» —
   одиночные кандидаты доступны только через инструмент `recall` и в промпт
   автоматически не попадают.
2. **Явная просьба пользователя** — панель «Память» в «Деталях» (кнопка «+»)
   или фраза «запомни…» для модели: инструмент `remember(text, kind)`. Такие
   записи сразу считаются подтверждёнными.
3. **Инструменты модели** — `remember` (запомнить), `recall` (поиск,
   включая неподтверждённых кандидатов), `forget` (забыть по id),
   `task_note` (заметка в рабочую память ветки).

**Рабочая память (`task`)** обновляется любым сжатием: Sticky Facts извлекает
строку «ЗАДАЧА:» из блока фактов, Summary заканчивает сводку строкой
«ЗАДАЧА: …» (она уходит в рабочий слой и не показывается в тексте сводки).
Заметки (`notes`) пополняет инструмент `task_note`. Чтобы модель действительно
им пользовалась (например, при пустом системном промпте), с каждым запросом
уходит системная подсказка: «как только пользователь называет задачу, срок,
договорённость или ограничение — вызывай task_note». Заметка, формулирующая
саму цель задачи («Задача: …»), переписывает поле `task`, а не добавляется
в список заметок. Задача также заполняется из сжатий: строка «ЗАДАЧА: …»
в конце сводки (Summary) или факты Sticky Facts.

Подбор релевантных фактов — по совпадению ключевых слов ключа записи с
последним сообщением пользователя (стандартная библиотека, без эмбеддингов);
попадание в промпт увеличивает счётчик использования записи — «холодные»
записи вытесняются первыми при переполнении (лимит 200 записей на модель).
Очистка по слоям: `POST /api/reset` с `{"scope":…}` — `"chat"` (по
умолчанию) удаляет чат и краткосрочный слой, сохраняя рабочую память;
`"history"` — краткосрочную и рабочую; `"working"` — только рабочий слой
ветки; `"long"` — только долговременные записи текущей модели; `"all"` — все
уровни всех моделей. Те же слои можно чистить корзинами в блоках панели
«Память». `/api/memory`
(GET/POST/DELETE) позволяет работать со слоем напрямую. Слои и фактически подставленный долговременный
блок последнего запроса видны в панели «Детали» («Память»).

Готовый сценарий проверки всех трёх слоёв в чате — кнопка **«Проверка
памяти»** в панели быстрого запуска (пресет `memory-check`, викторина в меню
«+»); пошаговая инструкция и чек-лист — в `MEMORY_SCENARIO.md`.

Независимо от файла на диске, временные данные панели «Детали» (последний
запрос/ответ, шаги, токены, время, ошибка) хранятся только в памяти и в файл
не попадают.

## Инструменты агента (function calling)

Модель в этом чате умеет вызывать локальные инструменты, когда это уместно.
Инструменты описываются как OpenAI-совместимые `tools` в запросе к
`/chat/completions`; когда модель запрашивает вызов, сервер выполняет его
локально (не обращаясь к API) и подставляет результат обратно в диалог, после
чего модель продолжает генерацию. Весь обмен проходит внутри одного ответа —
пользователь видит только итоговый текст.

Доступные инструменты:

| Инструмент | Параметры | Результат |
|---|---|---|
| `get_current_time` | `region` (string) — IANA-таймзона, например `Europe/Moscow` | Текущие дата и время в регионе (`2006-01-02T15:04:05Z07:00 (Europe/Moscow)`). |
| `roll_dice` | — | Случайное целое от 1 до 6 (именно игральный кубик d6), каждое с равной вероятностью. |

Как это работает:

- `tools.go` описывает инструменты (`Definitions`), исполняет их
  (`Execute`) и крутит цикл вызова (`RunLoop`): пока модель запрашивает
  инструменты, они выполняются и их результат возвращается модели. Число
  раундов ограничено: в интерфейсе — ползунком «Максимальное количество
  циклов» (1–10), вне интерфейса — `maxToolRounds` (6).
- `api/client.go` передаёт `tools` в запросе и умеет собирать фрагментированные
  `tool_calls` из потока (SSE).
- Инструменты доступны и в веб-чате, и в CLI чате (`go run ./app` /
  `go run ./app -cli`), а также в разовом запросе.

Примеры:

```sh
go run ./app "Сколько сейчас времени в Токио?"
go run ./app "Брось кубик"
```

## Безопасность

- `.env`, `.idea/` и `bin/` уже в `.gitignore` в корне проекта — поэтому секреты
  и артефакты не попадают в репозиторий.
- Не передавайте ключ флагом `-api-key` в общих системах: он остаётся в истории
  shell.
- Приложение не хранит **API-ключ** на диске и не включает его в историю.
  Детали запроса/ответа для панели «Детали» живут только в памяти. Единственное,
  что пишется на диск, — **контекст беседы и память** в базе SQLite в папке
  `history/` (`history/chat.db`), чтобы диалог и долговременная память
  сохранялись между перезапусками. Учтите: база содержит текст беседы в
  открытом виде; при необходимости держите её вне репозитория и не публикуйте.
