# ai-chat-go — Task14

Чат с ИИ через OpenAI-совместимый API с веб-интерфейсом в стиле плоского
мессенджера (бирюзовая тема). Написан на Go: стандартная библиотека +
pure-Go драйвер SQLite (`modernc.org/sqlite`, без cgo) для сохранения
контекста и памяти.

> Task14 — чат с **инвариантами**: жёсткие правила ассистента, которые
> хранятся **отдельно от диалога** (SQLite-таблицы `invariants` +
> `invariants_log`, глобально для всех вкладок) и **не могут быть нарушены
> ни при каких условиях**. Каждый ответ перед выдачей проходит **гейт —
> проверку кодом**, а не просто запрет в промпте: этап 1 —
> детерминированные regex-шаблоны, этап 2 — LLM-судья (strict-JSON вердикт,
> fail-closed при любой ошибке, общий бюджет = «Допустимый таймаут
> ответа»); при активных инвариантах ответ буферизуется — в сеть не уходит
> ни байта до вердикта, нарушенный черновик заменяется отказом «🛡». Модель
> **не может изменить инварианты из диалога** — только пользователь:
> панель «Инварианты» в «Настройках» (список, тумблеры, инлайн-правка,
> выбор модели судьи), слэш-команды CLI `/invariant …`, автосев
> `AI_INVARIANTS` при первом старте. Каждое изменение пишется в **журнал
> аудита** (что → на что, когда, источник: ui/cli/env_seed). Плюс всё из
> Task13: вкладки с трёхслойной памятью, конечные автоматы (состояние
> задачи `task_state` и анкета онбординга), сжатие контекста, ветвление,
> инструменты, независимые резервы `[reserve]` и `[small]` (дешёвая
> не-reasoning модель — кандидат в судьи).

## Возможности

- Веб-чат в браузере: локальный сервер + страница-мессенджер (бирюзовая тема).
- Потоковый вывод (SSE) прямо в окно чата.
- Поддержка reasoning-моделей: трейс `reasoning`/`reasoning_content`
  не показывается, но считается «активностью» и не даёт оборвать долго
  думающую модель.
- **Вкладки чатов**: панель вкладок в шапке — клик переключает, «×»
  закрывает, кнопка «+» создаёт новую. Нумерация «Чат N»
  **динамическая**: новая вкладка получает номер «максимум + 1», а после
  закрытия оставшиеся вкладки сдвигаются, закрывая дыры («Чат 3»
  становится «Чат 2»); перенумерация переживает перезапуск (титулы
  пишутся в базу), кастомные заголовки без номера не трогаются.
  Последнюю вкладку закрыть нельзя.
- **Каждая вкладка — отдельный контекст**: сообщения, ветки, рабочая
  память (задача/заметки/факты) и **долговременная память** принадлежат
  вкладке (сессии), а не модели. Модель выбирается **в пределах вкладки**;
  смена модели не трогает её память — сессия перерегистрируется под новой
  моделью, долговременная память остаётся за вкладкой.
- **Закрытие вкладки** удаляет весь контекст вкладки одной транзакцией:
  сообщения, ветки, состояние сессии и все записи её долговременной памяти.
  После закрытия контекст в базе не остаётся.
- **Корзина в шапке** — контекстное меню; все пункты применяются **только
  к текущей вкладке** (другие вкладки не затрагиваются):
  **«Удалить чат»** — сообщения и краткосрочный слой (рабочая память
  сохраняется); **«Удалить историю»** — краткосрочную и рабочую память
  (долговременная остаётся); **«Удалить все»** — все уровни памяти этой
  вкладки, включая долговременную (с подтверждением).
- **Блобы-профилей** над строкой ввода: три профиля из
  `testdata/profiles/user-profiles.txt` («Ребенок», «Изобретатель»,
  «Программист») — цветные блобы одинакового размера (120×36 px) в
  приглушённых цветах палитры. Клик отправляет **самопрезентацию профиля**
  как обычное сообщение в текущей вкладке.
- **Состояние задачи (конечный автомат)**: текущая задача вкладки ведётся
  как автомат `planning → execution → validation → done` (с откатом
  `validation → execution` и новой задачей из `done`) — текущий этап, шаг,
  ожидаемое действие и чек-лист плана. Этап меняет **только модель**
  инструментом `task_state` (один переход этапа за ответ; `done` требует
  полностью выполненного плана; сжатие контекста этап не двигает),
  интерфейс — **только дисплей**: чип «⚙ execution · 2/4» над строкой
  ввода и блок «Задачи» в панели «Детали». Переходы строгие:
  недопустимые отклоняются с причиной. См. «Состояние задачи».
- **Онбординг: анкета нового пользователя**: на новой вкладке модель
  проводит интервью по скрипту (`interview → confirm → done`), ответы
  сразу попадают в долговременную память вкладки как факты профиля;
  обязательный вопрос пропустить по одному нельзя, всю анкету — можно;
  до конца анкеты остальные инструменты заблокированы. См. «Онбординг».
- **Инварианты ассистента**: жёсткие правила вне диалога, которые модель
  не может нарушить — ответ перед выдачей проверяется кодом (regex +
  LLM-судья), нарушенный черновик заменяется отказом. Меняются только
  явной командой пользователя, каждое изменение — в журнале. См.
  «Инварианты».
- **Меню кнопки «+»** слева от поля ввода: десять готовых вопросов по
  программированию (история и люди, общие концепции, написание кода;
  один — с просьбой объяснить). Клик по вопросу отправляет его как обычное
  сообщение в текущей вкладке; меню закрывается.
- **Панель «Память»** (в «Деталях»): три блока по слоям — краткосрочный,
  рабочий, долговременный — с текущим содержимым, **объёмом слоя в
  токенах** и **тумблером включения** у каждого (выключенный слой не
  попадает в промпт, данные сохраняются). Переключение — `POST
  /api/memory/layers`. Долговременный блок — **текущей вкладки**.
- **Сжатие контекста на лету**: при превышении «Порога контекста» старые
  сообщения сворачиваются выбранной стратегией без действий пользователя;
  в чате — плашка «Сжатый контекст · показать сводку». Стратегии:
  **Summary**, **Sliding Window**, **Sticky Facts** — см. «Сжатие
  контекста».
- **Ветвление диалога** в стиле ChatGPT: «Ветвление отсюда»,
  «Переспросить», переключатель «⟨ 1/2 ⟩» — см. «Ветвление диалога».
- **Инструменты агента (function calling)**: `get_current_time(region)`,
  `roll_dice()` и память `remember` / `recall` / `forget` / `task_note`.
  См. «Инструменты агента».
- **Markdown-форматирование** сообщений: заголовки, списки,
  жирный/курсив/зачёркнутый, код, ссылки, цитаты, таблицы GFM
  (`|---|---|`).
- **Панель «Детали»** (`GET /api/debug`): «Запрос» (последний чат-обмен),
  «Шаги» (пошаговый лог с токенами раундов и вложенными шагами),
  «Количество токенов», «Память», «Сжатие» и «Ошибка».
- **Ползунки** в панели настроек: `max_tokens` ответа (1–15 000; при
  открытии страницы — по максимуму), таймаут ответа (5–30 с, по умолчанию
  20 с), максимальное количество циклов инструментов (1–10, по умолчанию
  6), «Порог контекста» (5–40, по умолчанию 10) и «Количество сообщений»
  (3–30, по умолчанию 5).
- **Управление форматом ответа** из интерфейса: `text`, `json`,
  `jsonschema`, `jsonschema_structured` (strict), плюс `stop`-последовательность.
- **Список моделей обновляется автоматически** при загрузке страницы из
  `GET {AI_BASE_URL}/models`; не-чат модели (embeddings/reranker/whisper)
  отфильтровываются по имени. Если API недоступен — фолбэк на `AI_MODELS`
  или `DefaultModels`.
- **Резервный провайдер `[reserve]`**: независимый OpenAI-совместимый
  эндпоинт, отдельный от основного; включается, когда основной
  недоступен; в сайдбаре — пунктирным контактом.
- **Маленькая модель `[small]`**: второй независимый резерв — дешёвая
  НЕ-reasoning модель с внешнего провайдера (по умолчанию
  `openai/gpt-4.1-nano` через polza.ai); выбирается в списке моделей и
  подходит на роль судьи инвариантов (строгий JSON при малом лимите токенов).
- **Понятные ошибки больших запросов**: тело `POST /api/chat` принимается
  до 64 МБ; при превышении — «Сообщение слишком большое», при невалидном
  JSON — причина разбора; обе ошибки попадают в чат и в блок «Ошибка».
- **Сохранение контекста и памяти между перезапусками** в SQLite
  `history/chat.db`: вкладки, их история, ветки, рабочая и долговременная
  память (см. «Сохранение контекста»).
- Терминальный режим (`-cli`) и разовый запрос из командной строки.
- Системный промпт, смена модели (в пределах вкладки), настройка лимита
  токенов и таймаута.
- Конфигурация через переменные окружения, файл `.env` или флаги.

- Go 1.22 или новее.

```sh
cd Task14

```

```sh
export AI_API_KEY="sk-..."

```

```sh
go run ./app "Привет! Кто ты?"
```

## Использование

```sh
go run ./app                            # веб-чат: сервер + браузер
go run ./app -cli                       # чат в терминале
go run ./app "Объясни, что такое горутина"

go run ./app -system "Отвечай только по-русски"
```

### Веб-интерфейс

При запуске без аргументов клиент поднимает сервер на `http://127.0.0.1:5190`
и открывает его в браузере (бирюзовый мессенджер с пузырями сообщений). Если
порт занят, берётся следующий свободный. Сервер слушает только `127.0.0.1`,
переписка не покидает компьютер. Страница умеет:

- вести **несколько вкладок чата**: «+» в шапке создаёт вкладку («Чат N» —
  номер = максимум + 1), «×» закрывает (контекст вкладки удаляется), клик
  переключает; модель и весь контекст — у каждой вкладки свои;
- отправлять сообщения (Enter или кнопка с бумажным самолётиком) — ответ
  стримится по мере поступления токенов, с **Markdown-разметкой**;
- отправлять **самопрезентацию профиля** кликом по блобу над строкой ввода
  и **готовые вопросы** из меню кнопки **«+»** слева от поля ввода;
- очищать контекст **текущей вкладки** корзиной в шапке («Удалить чат» /
  «Удалить историю» / «Удалить все»);
- **ветвить диалог**: «Ветвление отсюда» на сообщении пользователя,
  «Переспросить» на ответе модели, переключатель «⟨ 1/2 ⟩»;
- выбирать модель в боковом меню (модель вкладки), в том числе резервную;
- настраивать `max_tokens`, таймаут ответа, число циклов инструментов,
  порог и окно сжатия, стратегию сжатия;
- включать/выключать слои памяти в панели «Память» и смотреть содержимое
  слоёв текущей вкладки;
- выбирать формат ответа (`text` / `json` / `jsonschema` /
  `jsonschema_structured`) и задавать `stop`-последовательность;
- смотреть «Детали» (запрос/ответ, «Шаги», токены, память, сжатие,
  диагностика) через `GET /api/debug`;
- после перезагрузки страницы и приложения вкладки, их история и память
  восстанавливаются из SQLite.

Чтобы браузер не открывался автоматически, добавьте `-no-open`.

### Флаги

| Флаг | Описание |
|---|---|
| `-base-url` | Базовый URL API. |
| `-api-key` | API-ключ (лучше через `AI_API_KEY`, чтобы ключ не попал в историю команд). |
| `-model` | Имя модели. |
| `-system` | Системный промпт. |
| `-max-tokens` | Максимум токенов ответа. |
| `-timeout` | Таймаут запроса, например `2m`. |
| `-no-stream` | Не использовать потоковый вывод. |
| `-web` | Веб-интерфейс с открытием в браузере (по умолчанию `true`). |
| `-cli` | Терминальный чат вместо веб-страницы. |
| `-port` | Порт веб-интерфейса (по умолчанию `5190`). |
| `-no-open` | Не открывать браузер автоматически. |

`ai-chat -h` покажет справку.

### Команды в терминальном режиме (`-cli`)

| Команда | Действие |
|---|---|
| `/help` | Показать справку. |
| `/reset` | Очистить историю диалога. |
| `/model` | Показать текущую модель. |
| `/model <имя>` | Переключить модель. |
| `/system` | Показать системный промпт. |
| `/system <текст>` | Задать системный промпт и очистить историю. |
| `/invariant` | Показать инварианты и последние изменения журнала. |
| `/invariant add <текст>` | Добавить инвариант (regex-шаблоны — через панель или API). |
| `/invariant edit <id> <новый текст>` | Изменить формулировку (старое → новое пишется в журнал). |
| `/invariant rm <id>` | Удалить инвариант. |
| `/invariant on <id>` / `/invariant off <id>` | Включить/выключить участие в гейте. |
| `/exit`, `/quit` | Выйти. |

## Как это работает

Клиент отправляет `POST {AI_BASE_URL}/chat/completions` с заголовком
`Authorization: Bearer <AI_API_KEY>` и телом в формате OpenAI Chat
Completions. В потоковом режиме ответ читается как Server-Sent Events:
строки `data: {...}` разбираются, из `choices[].delta.content` собирается
текст, `data: [DONE]` завершает поток. Токены
`choices[].delta.reasoning_content`/`reasoning` (трейс думающей модели) не
показываются, но регистрируются как активность, чтобы не оборвать
генерацию.

Веб-интерфейс работает так: браузер шлёт `POST /api/chat` с JSON
`{"message": "...", "format": ..., "maxTokens": ..., "timeout": ...,
"schema": ..., "stop": ..., "compress": {...}}`, сервер вызывает API и
пересылает токены ответа в тело HTTP-ответа по мере поступления; страница
читает поток через `ReadableStream` и дорисовывает текст в реальном
времени. Блок `compress` задаёт настройки сжатия: `{"enabled": bool,
"strategy": "summary"|"sliding"|"sticky", "keep": N}` — сервер применяет их
на лету после каждого обмена. История хранится на сервере в виде дерева
сообщений **в пределах вкладки** и отдаётся через `GET /api/history`
(каждое сообщение с `id` и `alts`, плюс `active` — см. «Ветвление
диалога»); кроме того, она сохраняется на диск между перезапусками.

Если модель во время ответа вернула ошибку, сервер дописывает в поток
пометку `[ошибка: …]`: клиент показывает её сообщением об ошибке, а
вопрос пользователя остаётся в чате (сервер откатывает незавершённый
обмен, поэтому перечитывать историю в этот момент нельзя).

Диагностика доступна через `GET /api/debug` и возвращает детали для панели
«Детали»: последний чат-запрос/ответ (сжатие не перезатирает), лог `steps`
за диалог (раунды — со своими `prompt_tokens`/`completion_tokens`,
инструменты и сжатия — во вложенных `sub`-шагах), суммарные `tokens`,
`prompt_tokens`, `completion_tokens`, `history_tokens`, накопительные
`total_prompt_tokens`, счётчик сжатий `compress_seq`, текущий блок `facts`
и последнее сжатие `last_compress`.

## Вкладки и контекст

Каждая вкладка чата — отдельная **сессия** с независимым контекстом:
своим деревом сообщений, ветками, рабочей памятью (задача/заметки/факты
активной ветки) и **долговременной памятью**. Долговременная память
ключится по сессии, а не по модели: два чата на одной модели имеют разные
долговременные памяти, а смена модели внутри вкладки память не трогает
(сессия перерегистрируется под новой моделью).

Поведение:

- **Создание вкладки** — «+» в шапке или `POST /api/tab`
  (`{"action": "new", "model": ...}`); заголовок «Чат N», где N =
  максимальный номер среди открытых вкладок и сохранённых сессий + 1.
- **Динамическая перенумерация** — при закрытии вкладки оставшиеся
  сдвигаются, закрывая дыры («Чат 3» становится «Чат 2»); при старте
  сервера дыры схлопываются так же. Титулы пишутся в базу
  (`session_state.title`), кастомные заголовки без номера «Чат N» не
  трогаются и номеров не потребляют.
- **Переключение** — клик по вкладке или `POST /api/tab`
  (`{"action": "select", "session": id}`); состояние уходящей вкладки
  снимается «снапшотом» и сохраняется.
- **Закрытие** — «×» на вкладке или `DELETE /api/tab?session=id`: из
  памяти и из базы одной транзакцией удаляются **все три слоя**
  (`DeleteSessionAll`) — сообщения, ветки, состояние сессии и вся
  долговременная память вкладки. Фокус переходит к соседней вкладке;
  последнюю вкладку удалить нельзя (`400`).
- **Корзина в шапке** — `POST /api/reset` со скоупом; все скоупы
  действуют **только на текущую вкладку**: `"chat"` (по умолчанию) —
  чат и краткосрочный слой; `"history"` — ещё и рабочую память;
  `"working"` — только рабочую память ветки; `"long"` — только
  долговременную память вкладки; `"all"` — все уровни вкладки, включая
  долговременную (в интерфейсе — с подтверждением).

API вкладок:

| Endpoint | Описание |
|---|---|
| `GET /api/tabs` | Список вкладок: `id`, заголовок, модель + `active`. |
| `POST /api/tab` | `{"action": "new", "model": ...}` — новая вкладка; `{"action": "select", "session": id}` — переключение. |
| `DELETE /api/tab` | `?session=id` — закрыть вкладку и удалить весь её контекст; последнюю — `400`. |
| `POST /api/model` | Сменить модель **текущей вкладки** (контекст сохраняется). |

## Сохранение контекста (истории)

Веб-чат сохраняет диалоги всех вкладок между перезапусками. Контекст
хранится в **SQLite** (`modernc.org/sqlite`, pure Go, без cgo): одна база
на все вкладки, путь задаётся `AI_DB_FILE` (по умолчанию
`history/chat.db`). Старые JSON-файлы (`history/.chat-history-<модель>.json`)
мигрируются в базу автоматически при первом запуске и помечаются
`*.migrated` — ничего не теряется. Пустой `AI_DB_FILE` отключает
сохранение.

База устроена по слоям памяти (см. следующий раздел): у диалога, рабочего
состояния веток и долговременной памяти — отдельные таблицы, все строки
несут ключ **`(model, session)`** (долговременная — **`session`**):

- **Таблицы** — `messages` (дерево сообщений: `id`/`parent`, роль, текст,
  `tool_calls`, время), `branches` (состояние каждой ветки: CoveredUpTo,
  сводка, блок фактов, задача, заметки, токены), `session_state` (активная
  ветка, `next_id`, счётчики токенов) и `memories` (долговременная память:
  `PRIMARY KEY (session, id)`, `UNIQUE (session, kind, key)`).
- **Когда пишется** — после каждого изменения истории: завершённого
  обмена, новой вкладки, смены модели, ветвления/переключения. Запись —
  одной транзакцией (`storage.SaveSession`).
- **Когда читается** — при старте сервера: восстанавливаются все
  сохранённые вкладки, активной становится сессия с самой свежей
  репликой.
- **Удаление** — только явно: закрытие вкладки удаляет её строки
  (`DeleteSessionAll`), корзина чистит выбранные слои текущей вкладки.
  Папка `history/` исключена из git.

## Память: три слоя

Информация диалога разделена на три типа памяти. Слои хранятся отдельно,
наполнение каждого — явное, и для каждого слоя определено правило, что
именно попадает в промпт. **Все три слоя — на вкладку**: контекст вкладок
полностью независим.

| Слой | Что хранит | Где хранится | Что идёт в промпт |
|---|---|---|---|
| **Краткосрочная** | текущий диалог вкладки | таблица `messages` (дерево с ветками, ключ `(model, session)`) | последние `keep` сообщений активной ветки дословно (окно автосжатия) |
| **Рабочая** | данные текущей задачи вкладки | таблица `branches` (задача `task`, заметки `notes`, сводка `summary`, факты `facts`) | блок «Рабочая память текущей задачи» (задача + заметки) и «Блок важных фактов» — всегда, одной system-строкой |
| **Долговременная** | профиль, решения, знания вкладки | таблица `memories` (**ключ — сессия/вкладка**) | профиль — всегда (до 10 строк); решения и знания — при совпадении темы вопроса, бюджет ~600 токенов |

Как наполняется долговременная память (явная маршрутизация записи):

1. **Факты сжатия — основной канал.** При сжатии Sticky Facts модель ведёт
   блок «ключ: значение» и возвращает цель задачи (`ЗАДАЧА:`) и факты с
   тегами (`[профиль]`, `[решение]`, `[знание]`). Каждая строка факта
   дедуплицируется по ключу и попадает в таблицу `memories` **текущей
   вкладки**. Факт, подтверждённый двумя сжатиями подряд
   (`confirmations ≥ 2`), становится «долговременным» — одиночные
   кандидаты доступны только через инструмент `recall` и в промпт
   автоматически не попадают.
2. **Явная просьба пользователя** — панель «Память» в «Деталях» или фраза
   «запомни…» для модели: инструмент `remember(text, kind)`. Такие записи
   сразу считаются подтверждёнными.
3. **Инструменты модели** — `remember` (запомнить), `recall` (поиск,
   включая неподтверждённых кандидатов), `forget` (забыть по id),
   `task_note` (заметка в рабочую память ветки).

**Рабочая память (`task`)** обновляется любым сжатием: Sticky Facts
извлекает строку «ЗАДАЧА:» из блока фактов, Summary заканчивает сводку
строкой «ЗАДАЧА: …». Заметки (`notes`) пополняет инструмент `task_note`.
**Состояние задачи** (`task_state`, конечный автомат — см. «Состояние
задачи») живёт в том же рабочем слое и переживает «Удалить чат».

Подбор релевантных фактов — по совпадению ключевых слов ключа записи с
последним сообщением пользователя (стандартная библиотека, без
эмбеддингов); попадание в промпт увеличивает счётчик использования —
«холодные» записи вытесняются первыми при переполнении (лимит 200
записей **на вкладку**). Очистка по слоям — `POST /api/reset` со скоупом
(все скоупы — текущей вкладки; см. «Вкладки и контекст»); `/api/memory`
(GET/POST/DELETE) работает с долговременным слоем текущей вкладки.

## Состояние задачи (конечный автомат)

Текущая задача вкладки ведётся как строгий конечный автомат (FSM) в
рабочем слое памяти ветки: **этап** (`stage`), **текущий шаг** (`step`),
**ожидаемое действие** (`expect`) и **чек-лист плана** (`plan` — шагу
присвоен статус `pending` / `active` / `done`, активным может быть не
больше одного шага).

Переходы между этапами строго ограничены:

| Откуда | Куда |
|---|---|
| (нет задачи) | `planning` — создать задачу |
| `planning` | `execution` — начать выполнение (**только после утверждённого плана** — без плана переход отклоняется кодом); `reset` — отменить задачу |
| `execution` | `validation` — проверка результата |
| `validation` | `done` — принять результат; `execution` — откат при проблемах |
| `done` | `planning` — новая задача |

Любой другой переход отклоняется сервером с объяснением допустимых
переходов (`400` в HTTP, текст причины — в результате инструмента).

Управляет автоматом **только модель** — инструмент `task_state`
(действия `get` / `advance` / `set` / `plan` / `reset`). Результат вызова
— отрендеренное состояние автомата, поэтому модель сразу видит эффект.
Жёсткие гарантии сервера:

- **Один переход этапа за ответ.** Счётчик переходов сбрасывается в
  начале каждого `/api/chat`; второй переход этапа в том же ответе
  отклоняется («этап уже менялся в этом ответе…»). Запись плана
  (`action=plan`) переходом не считается — «план + advance» в одном
  ответе возможны.
- **`done` требует выполненного плана.** Переход `validation → done`
  отклоняется, пока в чек-листе есть незакрытые шаги.
- **Сжатие контекста этап не двигает.** Summary и Sticky Facts просят
  модель перенести состояние строками `ЭТАП:` / `ШАГ:` / `ОЖИДАНИЕ:`, но
  сервер копирует из ответа только шаг и ожидание (и только если задача
  уже существует) — этап меняется исключительно инструментом.
- **UI — только дисплей.** Чип «⚙ execution · 2/4» над строкой ввода
  (клик открывает панель «Детали») и блок «Задачи»: степпер этапов,
  поля «Текущий шаг» / «Ожидаемое действие» (read-only) и чек-лист
  плана. Изменить состояние в интерфейсе нельзя — этап сдвигается
  только в диалоге с моделью.

Хранение и жизненный цикл:

- FSM хранится в поле `task_state` (JSON) таблицы `branches` — **на ветку**;
  при форке новая ветка получает **глубокую копию**, ветки не делят FSM.
- «Удалить чат» FSM **сохраняет** (он описывает задачу, а не сообщения);
  «Удалить историю» / «Удалить все» / «Удалить рабочую» и закрытие
  вкладки — удаляют. Смена модели на FSM не влияет.
- Состояние отправляется модели блоком в system-промпте рабочей памяти
  («Состояние задачи (конечный автомат …)»); тумблер «Рабочая» в панели
  «Память» выключает его вместе со всем рабочим слоем.
- Если FSM пустой, его нет: чип скрыт, поле в базе пусто.

API:

| Endpoint | Описание |
|---|---|
| `GET /api/task` | Состояние автомата активной ветки (`task: null`, если задачи нет). |
| `POST /api/task` | `{"stage", "step", "expect", "plan"}` — строгое обновление с той же таблицей переходов; пустое поле не меняет, `"stage":"reset"` отменяет задачу (только из `planning`). |

## Онбординг: анкета нового пользователя

Новая вкладка начинает диалог с **анкеты**: по встроенному скрипту
(`onboarding_questions.txt`, `go:embed`) модель задаёт вопросы по одному
и собирает профиль пользователя. Анкета — тоже строгий конечный автомат:

| Этап | Куда |
|---|---|
| (нет анкеты) | `interview` — старт на новой вкладке |
| `interview` | `interview` — следующий вопрос; `confirm` — все вопросы закрыты; `done` — прервать всю анкету (`onboarding_skip`, `all=true`) |
| `confirm` | `confirm` — поправить ответ по ключу; `done` — профиль подтверждён |
| `done` | финал; рестарт — только `POST /api/onboarding {"action":"restart"}` |

Правила:

- **Ответы сразу в долговременной памяти.** Каждый ответ сохраняется
  инструментом `onboarding_answer` как факт профиля (`kind=profile`,
  источник `onboarding`, сразу «долговечный») и попадает в промпт наравне
  с остальными записями долговременной памяти вкладки.
- **Обязательный вопрос по одному пропустить нельзя**: попытка
  `onboarding_skip` обязательного вопроса отклоняется с подсказкой
  ответить или прервать всю анкету. Необязательные вопросы пропускаются
  свободно; прервать можно только **всю анкету** (`all=true`).
- **Гейт инструментов**: пока анкета идёт (`interview`/`confirm`), вызов
  любого инструмента, кроме `onboarding_answer` / `onboarding_skip` /
  `onboarding_confirm`, отклоняется с объяснением — диалог не «съезжает»
  в посторонние задачи до конца анкеты.
- **Подтверждение**: на этапе `confirm` модель показывает сводку
  ответов; `onboarding_confirm` завершает анкету, правки — через
  `onboarding_answer` с ключом вопроса (анкета остаётся в `confirm`).

Интерфейс: блок «Задачи» в панели «Детали» показывает этап анкеты и
прогресс; кнопки «Подтвердить профиль» (этап `confirm`), «Пропустить
анкету» (скрыта после `done`) и «Пройти заново» (после `done`); чип
«❓ Анкета» над строкой ввода.

API:

| Endpoint | Описание |
|---|---|
| `GET /api/onboarding` | Состояние анкеты активной ветки (`onboarding: null`, если не начиналась). |
| `POST /api/onboarding` | `{"action": "skip"\|"confirm"\|"restart"}` — прервать анкету / подтвердить (только из `confirm`) / пройти заново. |

Хранение — как у автомата задачи: поле `onboarding` (JSON) в таблице
`branches`, **на ветку**, переживает перезапуск; закрытие вкладки
удаляет.

## Инварианты

Инварианты — жёсткие правила, которые модель **не может нарушить ни при
каких условиях**. Они хранятся отдельно от диалога: глобальная таблица
`invariants` в SQLite (без ключа сессии — общие для всех вкладок,
«Удалить чат» и закрытие вкладки их не трогают).

Гарантия держится кодом, а не промптом: пока включён хотя бы один
инвариант, ответ модели **буферизуется** и не отправляется клиенту, пока
гейт не проверит черновик. Этапы проверки:

1. **Детерминированный** — regex-шаблоны из поля `patterns` инварианта
   (`|`-разделённый список), бесплатный и мгновенный.
2. **LLM-судья** — отдельный non-streaming вызов с малым лимитом токенов
   и strict-JSON вердиктом `{"violated", "id", "reason"}`. Судья видит
   только инварианты и черновик (черновик — как данные внутри
   `<draft>`), без истории диалога — инъецировать его через переписку
   нельзя. Модель судьи: выбор в панели («Модель судьи», RAM-override),
   иначе `AI_INVARIANTS_JUDGE_MODEL`, иначе `qwen3.8-27b` — маленькая
   НЕ-reasoning модель, стабильно отвечающая контентом при малом лимите
   (reasoning-модели тратят бюджет на трейс). Сетевые сбои и обрезанный
   JSON ретраятся (до 3 попыток с растущим лимитом); общий бюджет этапа
   ограничен значением «Допустимый таймаут ответа» — при недоступности
   судьи гейт fail-closed'ится по дедлайну, а не висит минутами.

Нарушенный черновик **не выдаётся и не сохраняется**: клиент и история
получают отказ «🛡 **Отказано**: ответ нарушил бы инвариант №N — …»
(структурированный markdown: вердикт + подсказка, в чате — плашка
«🛡 Отказ по инварианту» после текста). Судья недоступен или вернул
не-JSON → fail-closed (отказ). Проверка выполняется и на
«Переспросить», и в терминальном режиме.

Создание и изменение — **только явная команда пользователя**:

| Способ | Действие |
|---|---|
| Панель «Инварианты» в «Настройках» (внизу, развёрнута по умолчанию) | добавить / инлайн-правка (текст + regex) / вкл-выкл / удалить, выбор модели судьи, сворачиваемая «История изменений» (`GET, POST, PATCH, DELETE /api/invariants`) |
| CLI: `/invariant add \| edit \| rm \| on \| off \| list` | то же из терминала |
| `AI_INVARIANTS` в `.env` | автосев **один раз** на пустой таблице (`source=env_seed`) |

Модель не имеет пути к изменению списка: у неё нет такого инструмента
(реестр инструментов фиксированный, неизвестные отклоняются кодом), а
просьбы «измени инвариант» из диалога отклоняются — об этом написано в
промпт-блоке инвариантов (первое system-сообщение каждого запроса;
модель знает правила и умеет отказывать сама, но это только первый
рубеж).

Каждое изменение пишется в журнал `invariants_log` **в одной транзакции
с изменением**: действие (`create/update/enable/disable/delete`), что →
на что, время, источник (`ui/cli/env_seed`). Журнал виден в панели
(блок «История изменений»); удалённая формулировка остаётся в
`old_value`. Пустой список инвариантов выключает гейт — работает
обычный стриминг.

Два вспомогательных механизма держат поведение предсказуемым. После
любого изменения списка модель получает **одноразовую системную
заметку** («список инвариантов только что изменил пользователь —
руководствуйся только актуальным списком, прежние отказы в истории
могли относиться к уже удалённым инвариантам») — без неё модель по
инерции продолжает отказывать, видя старые отказы в краткосрочной
истории. Отказ по инварианту показывается одним пузырём с плашкой и не
дублируется строкой ошибки в чате.

## Сжатие контекста

Когда сообщений в диалоге становится больше «Порога контекста» (ползунок
5–40, по умолчанию 10), контекст сжимается **автоматически, на лету** —
без каких-либо действий пользователя — до «Количества сообщений»
(ползунок 3–30, по умолчанию 5): столько последних сообщений остаётся как
есть. Стратегия выбирается в панели настроек (блок «Стратегия сжатия»):

| Стратегия | Как работает | Что видит модель | Плашка в чате |
|---|---|---|---|
| **Summary** (по умолчанию) | Модель составляет краткую сводку по удаляемой переписке | Сводка как системное сообщение + последние N сообщений | «Контекст сжат: …» |
| **Sliding Window** | Старые сообщения просто удаляются, без вызова модели | Только последние N сообщений | «Сжатие контекста (Sliding Window): …» |
| **Sticky Facts** | Модель ведёт блок фактов «ключ: значение»: при сжатии обновляет его по удаляемой переписке | Последние N сообщений + блок фактов первым сообщением | «Сжатие контекста (Sticky Facts): …» |

Детали:

- Настройки сжимаются в блок `compress` тела `/api/chat` и применяются на
  лету после каждого обмена; изменение настроек — `POST /api/compress`,
  если диалог уже больше порога, сжатие выполняется немедленно.
- Извлекаемые факты сжатия уходят в **долговременную память сжимаемой
  вкладки** (дедуп по ключу, повторные встречи поднимают подтверждения).
- В ветке сжимаются только её собственные сообщения: префикс до точки
  ветвления и сама точка остаются видимыми (см. «Ветвление диалога»).
- Факт сжатия хранится в истории: роль `summary` (сводка, уходит модели)
  или `marker` (служебная запись для интерфейса, модели не отправляется).
  В чате на этом месте — сворачиваемая плашка «Сжатый контекст · показать
  сводку».
- Блок «Сжатие» в «Деталях» показывает стратегию, число сжатых
  сообщений, токены вызова и результат с Markdown-форматированием; каждое
  сжатие попадает в «Шаги» вложенным шагом.

## Ветвление диалога

История чата хранится как дерево сообщений (у каждого `id` и ссылка на
родителя `parent`), а не линейный список. Это позволяет вести несколько
альтернативных продолжений одного диалога — как в ChatGPT — и
переключаться между ними, не теряя ни одну из веток. Ветвление ведётся в
пределах вкладки.

Интерфейс:

- **«Ветвление отсюда»** — иконка на сообщении пользователя: всё, что было
  после этого сообщения, остаётся на прежней ветке, а новые сообщения
  пойдут в новую (`POST /api/branch` с `{"after": id}`); новая ветка сразу
  становится активной.
- **«Переспросить»** — иконка на ответе модели: то же ветвление от
  вопроса, плюс сразу отправляется повторный запрос (`POST /api/chat` с
  `"regenerate": true`) — прежний ответ остаётся доступным через
  переключатель.
- **Переключатель «⟨ 1/2 ⟩»** — один на каждое ветвление; стрелки
  переключают ветки без обращения к модели (история просто
  перерисовывается). Пустые версии ответа считаются; пустой ответ модели
  отображается приглушённой пометкой «пустой ответ модели». Ветки
  восстанавливаются и после перезапуска приложения; если точка ветвления
  скрыта сжатием, её переключатель переносится на плашку «Сжатый
  контекст».

Детали:

- Видимая история — путь по дереву от корня до активного листа; сообщения
  других веток в контекст модели не попадают.
- **Сжатие контекста ведётся отдельно для каждой ветки**: сводка/факты и
  граница сжатого префикса хранятся у листа ветки.
- **Сжатие в ветке сворачивает только её собственные сообщения** — те, что
  появились после точки ветвления; унаследованная на момент форка сводка
  фиксируется «замороженной» плашкой.
- Во время генерации ответа операции с ветками возвращают `409 Conflict`.
- `DELETE /api/branch` удаляет ветку вместе с её уникальными сообщениями;
  активную ветку удалить нельзя (`409`).

API ветвления:

| Endpoint | Описание |
|---|---|
| `POST /api/branch` | `{"after": id}` — создать ветку после сообщения `id`. |
| `POST /api/branch/switch` | `{"id": id}` — переключиться на ветку с листом `id`. |
| `GET /api/branches` | Список веток: `id` листа, заголовок, число сообщений, `active`. |
| `DELETE /api/branch` | `{"id": id}` — удалить ветку (активную нельзя — `409`). |
| `GET /api/history` | `messages` + `active`; у каждого сообщения `id` и `alts`. |
| `POST /api/chat` | Флаг `"regenerate": true` — переспросить текущий вопрос заново. |

## Инструменты агента (function calling)

Модель в этом чате умеет вызывать локальные инструменты, когда это
уместно. Инструменты описываются как OpenAI-совместимые `tools` в запросе
к `/chat/completions`; когда модель запрашивает вызов, сервер выполняет
его локально и подставляет результат обратно в диалог, после чего модель
продолжает генерацию. Пользователь видит только итоговый текст.

| Инструмент | Параметры | Результат |
|---|---|---|
| `get_current_time` | `region` (string) — IANA-таймзона, например `Europe/Moscow` | Текущие дата и время в регионе. |
| `roll_dice` | — | Случайное целое от 1 до 6 (игральный кубик d6). |
| `remember` | `text`, `kind` (`profile`/`decision`/`knowledge`) | Запись в **долговременную память вкладки** (сразу подтверждённая). |
| `recall` | `query` | Поиск по записям долговременной памяти вкладки (включая неподтверждённые кандидаты); возвращает `id` для `forget`. |
| `forget` | `id` | Удаляет запись из долговременной памяти вкладки. |
| `task_note` | `text` | Заметка в **рабочую память** ветки (строка «Задача: …» переписывает поле задачи). |
| `task_state` | `action` (`get`/`advance`/`set`/`plan`/`reset`), `stage`, `step`, `expect`, `plan` (string[]), `completed` (int) | Строгое управление **состоянием задачи** (конечный автомат, см. «Состояние задачи»); недопустимый переход возвращается причиной; не более одного перехода этапа за ответ. |
| `onboarding_answer` | `answer`, `key` (обязателен в `confirm`) | Сохраняет ответ на вопрос анкеты как факт профиля в долговременной памяти (см. «Онбординг»). |
| `onboarding_skip` | `all` (bool) | Пропускает текущий **необязательный** вопрос; `all=true` прерывает всю анкету. Обязательный вопрос по одному пропустить нельзя. |
| `onboarding_confirm` | — | Завершает анкету из этапа `confirm`: профиль подтверждён. |

Как это работает:

- `tools.go` описывает инструменты (`Definitions`), исполняет их
  (`Execute`) и крутит цикл вызова (`RunLoop`): пока модель запрашивает
  инструменты, они выполняются, и результат возвращается модели. Число
  раундов ограничено: в интерфейсе — ползунком «Максимальное количество
  циклов» (1–10), вне интерфейса — 6.
- `api/client.go` передаёт `tools` в запросе и умеет собирать
  фрагментированные `tool_calls` из потока (SSE).
- Память-инструменты работают с активной вкладкой: `remember`/`recall`/
  `forget` — с её долговременным слоем, `task_note` — с её рабочей.
- Инструменты доступны и в веб-чате, и в CLI чате, и в разовом запросе.

Примеры:

```sh
go run ./app "Сколько сейчас времени в Токио?"
go run ./app "Брось кубик"
go run ./app "Запомни: я люблю горки"
```

## Безопасность

- `.env`, `.idea/` и `bin/` уже в `.gitignore` в корне проекта — секреты и
  артефакты не попадают в репозиторий.
- Не передавайте ключ флагом `-api-key` в общих системах: он остаётся в
  истории shell.
- Приложение не хранит **API-ключ** на диске и не включает его в историю.
  Детали запроса/ответа для панели «Детали» живут только в памяти.
  Единственное, что пишется на диск, — **контекст бесед и память вкладок**
  в базе SQLite в папке `history/` (`history/chat.db`), чтобы диалоги и
  долговременная память сохранялись между перезапусками. Учтите: база
  содержит текст бесед в открытом виде; при необходимости держите её вне
  репозитория и не публикуйте.
