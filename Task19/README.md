# ai-chat-go — Task19

Чат с ИИ через OpenAI-совместимый API с веб-интерфейсом в стиле плоского
мессенджера (бирюзовая тема). Написан на Go; внешние зависимости —
**официальный MCP SDK** (`github.com/modelcontextprotocol/go-sdk`) и
pure-Go драйвер SQLite (`modernc.org/sqlite`).

> Task19 — развитие Task18: тот же чат-**MCP-клиент-хаб** (несколько
> серверов, инструменты в общем списке function-calling, автозапуск
> собственного orbit-сервера) и **планировщик фоновых задач**. Главная
> новая фича — **предсказуемое поведение агента на многошаговых
> цепочках инструментов**. В orbit добавлены 7 цепочных инструментов:
> `elect_*` (подбор благоприятной даты, 4 шага) и `brief_*` (утренний
> брифинг города, 3 шага). Цепочка — state-машина на сервере: сессия
> (`election_id`/`brief_id`), поле `next` указывает следующий шаг,
> guard'ы не дают выполнить шаг на пустых данных или вне порядка.
> Поведение модели закреплено системным промптом (`AI_SYSTEM`): при
> ошибке или пустом результате — остановиться и назвать шаг и причину.
> Тестовые сценарии цепочек — в блобе **«Цепочки»** (2 успешных + 4
> неявных негатива), раннер — `bin/chain-demo.py`. Планировщик Task18
> сохранён: горутина запускает задачи по расписанию, пока приложение
> работает (пропущенные запуски не догоняются). Задача — либо промпт
> (полноценный агентский ход), либо **прямой вызов MCP-инструмента**
> (поле `tool`: без модели — 0 токенов). Задачи и журнал запусков — в
> SQLite (`scheduler.db`); управление — блок **«Планировщик»** в
> сайдбаре, REST `/api/scheduler*` и команда `/sched` в CLI.
>
> По умолчанию подключены два сервера:
>
> | Slug | Сервер | Инструменты |
> |---|---|---|
> | `dubai` | Dubai Grocery Prices (`prices.brainy.ae/mcp`) — цены на продукты и стоимость жизни в ОАЭ | 19: сравнение корзин, цены магазинов, топливо, аренда, школа, налоги… |
> | `orbit` | Orbit MCP (`127.0.0.1:5199/mcp`) — **собственный MCP-сервер этой задачи** (папка `Task17_MCP`): астрология на реальной астрономии | 23: натальная карта, транзиты, синастрия, соляр, фаза Луны, брифинг дня, аффирмация, дневник наблюдений (3), пульс неба (3), SVG-колесо, статус… плюс **цепочки** `elect_*` (4) и `brief_*` (3) |
>
> Модель вызывает инструменты MCP наравне с локальными `get_current_time` и
> `roll_dice`, не зная о существовании протокола. Взаимодействие видно в
> интерфейсе: блок **«MCP»** в сайдбаре — карточка на каждый сервер (индикатор,
> число инструментов, **сворачиваемый** список инструментов, **тумблер
> вкл/выкл** и пиктограмма **⟳** для переподключения); чипы источника в панели
> **«Шаги»** — «🛒 Dubai Grocery Prices · 340 мс», «🔭 Orbit · 1,2 с»,
> «🕓 локально» (иконка по slug сервера), шаг с ошибкой
> **подсвечен красным**; длинные результаты вызовов свёрнуты до 600 символов.
> Статус — `GET /api/mcp`; в терминале — команда `/tools`.
>
> Отказоустойчивость: недоступный при старте сервер не мешает остальным
> (warning в консоли), фоновый цикл **автопереподключается каждые 60 с**,
> вызов при лежащем сервере падает быстро (fail-fast 30 с). Выключенный
> тумблером (или не подключённый) сервер **не передаёт инструменты модели**.

## Возможности

- **Планировщик фоновых задач** (наследие Task18): горутина внутри
  приложения запускает задачи по расписанию; два режима — промпт через
  модель или прямой вызов MCP-инструмента (`tool`); хранение и журнал —
  в SQLite; управление в сайдбаре, в «Деталях», по REST и в CLI (см.
  [«Планировщик фоновых задач»](#планировщик-фоновых-задач)).
- **Предсказуемые цепочки инструментов** (главная фича Task19):
  многошаговые цепочки `elect_*`/`brief_*` в orbit исполняются как
  state-машина на сервере, поведение агента закреплено системным
  промптом: агент не выдаёт результат, которого нет, не вызывает
  следующий шаг на пустых данных и сообщает, на каком шаге цепочка
  остановилась и почему (см. [«Цепочки инструментов orbit»](#цепочки-инструментов-orbit)).
- Веб-чат в браузере: локальный сервер + страница-мессенджер (бирюзовая тема).
- Потоковый вывод (SSE) прямо в окно чата.
- Поддержка reasoning-моделей: трейс `reasoning`/`reasoning_content`
  не показывается, но считается «активностью» и не даёт оборвать долго
  думающую модель.
- История диалога на сервере; кнопка «Новый диалог» (очистка истории).
- **Список моделей обновляется автоматически** при загрузке страницы из
  `GET {AI_BASE_URL}/models`; не-чат модели (embeddings/reranker/whisper)
  отфильтровываются по имени. Если API недоступен — фолбэк на `AI_MODELS`
  или `DefaultModels`.
- **Резервный провайдер `[reserve]`**: независимый OpenAI-совместимый эндпоинт
  (по умолчанию OpenCode Zen / DeepSeek), отдельный от основного GPUStack.
  Включается, когда основной недоступен; в сайдбаре отображается пунктирным
  контактом.
- **Управление форматом ответа** из интерфейса: `text`, `json`, `jsonschema`,
  `jsonschema_structured` (strict), плюс `stop`-последовательность.
- Панель **«Детали»** (`GET /api/debug`): последний запрос/ответ, пошаговый лог
  «Шаги» (включая вызовы инструментов с параметрами и результатом), суммарное
  количество токенов и общее время, а также диагностика (ошибка API, «нет
  ответа», превышение лимита токенов, нарушение JSON-схемы); блок
  **«Планировщик · лог»** — журнал последних запусков всех задач (свежие сверху;
  у упавшего запуска текст ошибки — в свёрнутом виде).
- Ползунки **`max_tokens`** и допустимого **таймаута ответа** (5–30 с) в интерфейсе.
- Терминальный режим (`-cli`) и разовый запрос из командной строки.
- Системный промпт, смена модели, настройка лимита токенов и таймаута.
- Конфигурация через переменные окружения, файл `.env` или флаги.
- **Инструменты агента (function calling)** доступны модели в чате:
  `get_current_time(region)` — текущие дата/время в заданном регионе (IANA);
  `roll_dice()` — случайное целое от 1 до 6 (именно игральный кубик; для
  подбрасывания монеты модель отвечает случайно, без инструмента). Модель сама
  решает, когда их звать; выполнение и подстановка результата происходят
  автоматически, невидимо для пользователя.
- **Интеграция MCP** (`AI_MCP_URLS` / флаг `-mcp-urls`, по умолчанию все три
  сервера выше): официальный Go SDK (`modelcontextprotocol/go-sdk`), транспорт
  Streamable HTTP, `initialize`-рукопожатие при старте (серверы подключаются
  параллельно), `tools/list` → инструменты всех серверов попадают в общий
  список function-calling; вызовы маршрутизируются в сервер-владелец
  (`tools/call`) с ретраем при сбросе сессии. **Коллизии имён**: инструмент,
  встречающийся у нескольких серверов (например, `search_products`), выдаётся
  модели с префиксом slug — `dubai__search_products` / `orbit__search_products`;
  уникальные имена сохраняются как есть. MCP недоступен — приложение работает дальше без
  него (warning в консоли): клиент **автопереподключается каждые 60 с** и
  подменяет список инструментов после успеха; пиктограмма **⟳** на карточке
  сервера форсирует коннект вручную (`POST /api/mcp/reconnect`); вызов
  инструмента при недоступном сервере падает быстро (fail-fast 30 с после
  неудачи, таймаут вызова `AI_MCP_TIMEOUT`, по умолчанию 30 с).
- **Тумблер вкл/выкл на каждый MCP-сервер**: выключенный сервер отключается,
  его инструменты **исключаются из списка, передаваемого модели** (как и у
  любого неподключённого сервера), фоновое переподключение его не трогает;
  включение подключает сервер заново. `POST /api/mcp/toggle`
  (`{"slug": "dubai", "enabled": false}`).
- **Видимость MCP в UI**: блок «MCP» в сайдбаре — карточка на каждый сервер
  (зелёный/красный индикатор, название, число инструментов, **сворачиваемый
  список инструментов с описаниями — по умолчанию свёрнут**; выключенный
  сервер приглушён с пометкой «выкл»), `GET /api/mcp`; в панели «Шаги» — чип
  источника вызова с **названием сервера и иконкой по slug**
  («🛒 Dubai Grocery Prices · 340 мс» / «🔭 Orbit · 1,2 с» / «🕓 локально»);
  шаг, вернувший ошибку (результат начинается с `ошибка:`), **подсвечен
  красным** — чип, заголовок и текст результата; длинные результаты свёрнуты
  до 600 символов с кнопкой «показать целиком».
- **Markdown-форматирование** сообщений: заголовки, маркированные/нумерованные
  списки, **таблицы GFM** (`| a | b |` + `|---|---|`), жирный/курсив/
  зачёркнутый, код (строчный и блочный), ссылки, цитаты, а также
  **сворачиваемые блоки** `<details><summary>…</summary>…</details>` — длинные
  вставки прячутся под кликабельный заголовок; и **«живой» SVG**: блок
  `<svg>…</svg>` (например, колесо натальной карты от `chart_render`) и фенс
  ```` ```svg ```` рендерятся настоящим векторным рисунком (с санитизацией:
  скрипты и обработчики событий вырезаются); **картинки** (`![alt](url)`,
  `data:image/...` и URL на `.png/.jpg/.gif/.webp/.svg` отдельной строкой)
  показываются прямо в сообщении, клик открывает оригинал в новой вкладке;
  внутри `<details>` работает и markdown, и SVG.
- **Ползунок «Максимальное количество циклов»** (1–10, по умолчанию 6): сколько
  раундов модель может запрашивать инструменты (в одном раунде их может быть
  несколько — лимит на число раундов, а не на число вызовов).
- **Быстрые сообщения (блобы-группы)** над строкой ввода: «Локальные»,
  «Комбо», «Dubai Grocery Prices», «Orbit», «Пульс», «Цепочки» (MCP-группы
  выделены цветом темнее). Клик по блобу открывает **контекстное меню с
  тестовыми сообщениями** группы — клик по пункту отправляет его в чат.
  «Комбо» — запросы, требующие и локального инструмента, и MCP одновременно
  (например, «Сколько сейчас времени в Дубае? И сравни цены на молоко 1 литр
  в супермаркетах Дубая»); «Orbit» — по одному тестовому сообщению на каждый
  из инструментов сервера (карта, транзиты, синастрия, соляр, Луна,
  брифинг дня, SVG, статус); «Пульс» — запросы к инструментам пульса неба
  (агрегированный отчёт `pulse_summary` за 24 часа / 3 часа / 1 час);
  «Цепочки» — сценарии `elect_*`/`brief_*`: два успешных (город Владимир)
  и четыре негатива в **неявных формулировках** (без упоминания `simulate`
  и ожидаемой реакции — проверка самостоятельного поведения модели).
- **Планировщик фоновых задач** (`scheduler/`): горутина внутри приложения,
  запускающая задачи по расписанию (`@every 30m`, `09:00`,
  `[пн,ср,пт] 09:00`, таймзоны IANA) **только пока приложение запущено**;
  пропущенные запуски не навёрстываются, вручную — кнопка «▶». Задача —
  промпт через модель **или прямой вызов MCP-инструмента** (поле `tool`,
  без модели — 0 токенов). Задачи и
  журнал запусков хранятся в SQLite (`scheduler.db`); блок **«Планировщик»**
  в сайдбаре (карточки задач: тумблер, «▶» — запустить сейчас, «✕» — удалить,
  форма «+ задача»); в CLI — команды `/sched`. Подробнее — раздел
  [«Планировщик»](#планировщик-фоновых-задач).

### Цепочка автозапуска

Одного запуска чата достаточно для всей астро-связки:
**чат → (mcpboot) orbit MCP → (супервизор orbit) Astrologer-API**. Перед
подключением к MCP чат проверяет `/api/status` локального сервера `orbit`
из `AI_MCP_URLS` и, если тот не отвечает, запускает его из `AI_MCP_DIR`;
orbit в свою очередь сам поднимает движок (см. `Task17_MCP/README.md`).
Поднятые процессы останавливаются при выходе из чата — и по обычному
завершению (EOF, `/exit`), и по Ctrl+C/`kill`: orbit получает SIGTERM,
успевает корректно остановить и свой движок (8 с льготы, затем SIGKILL).
Если orbit уже был запущен до старта чата, он не завершается вместе с чатом —
убитые извне процессы чат не трогает. На удалённые MCP-серверы автозапуск
не распространяется. Некорректно убить цепочку может только `kill -9` чата.

Изображения из результатов MCP-инструментов (например, SVG-колесо от
`orbit/chart_render`) показываются пользователю прямо в сообщении: клиент
чата сохраняет картинку в кэш (`~/Library/Caches/ai-chat-go/charts`), а
сервер раздаёт каталог по маршруту `GET /files/<имя>` и дописывает ссылку
в конец ответа (`![карта](http://…/files/…)`) — фронтенд рендерит её
инлайновой картинкой (клик открывает оригинал в новой вкладке). В контекст
модели пути и содержимое картинок не попадают — модель видит только
текстовую сводку инструмента.

Переменные окружения имеют приоритет над `.env`, флаги — над обоими.

## Использование

```sh
go run ./app                            # веб-чат: сервер + браузер
go run ./app -cli                       # чат в терминале
go run ./app "Объясни, что такое горутина"
go run ./app -model gpt-4o "Скажи что-нибудь"
go run ./app -no-stream "Ответь одним абзацем"
go run ./app -system "Отвечай только по-русски"
```

### Веб-интерфейс

При запуске без аргументов клиент поднимает сервер на `http://127.0.0.1:5190`
и открывает его в браузере (бирюзовый мессенджер с пузырями сообщений). Если
порт занят, берётся следующий свободный. Сервер слушает только `127.0.0.1`,
переписка не покидает компьютер. Страница умеет:

- отправлять сообщения (Enter или кнопка с бумажным самолётиком);
- показывать ответ по мере поступления токенов (включая трейс reasoning), с
  **Markdown-разметкой** и таблицами;
- отправлять сообщения через **блобы-группы** над строкой ввода: клик
  открывает контекстное меню с тестовыми сообщениями группы;
- «Новый диалог» (кнопка «+» в шапке) — очистить историю на сервере;
- выбирать модель в боковом меню; список обновляется из `/api/models`, для
  основной и резервной модели;
- настраивать `max_tokens` (ползунок), таймаут ответа (5–30 с) и **максимальное
  количество циклов** (ползунок 1–10);
- менять ширину панелей перетаскиванием: граница между «Настройками» и чатом
  (панель «Настройки» расширяется за счёт области чата) и между чатом и
  «Деталями»;
- выбирать формат ответа (`text` / `json` / `jsonschema` /
  `jsonschema_structured`) и задавать `stop`-последовательность;
- смотреть «Детали» (запрос/ответ, пошаговый лог «Шаги», токены, время и
  диагностику) через `GET /api/debug`;
- после перезагрузки страницы история восстанавливается (`GET /api/history`).

Чтобы браузер не открывался автоматически, добавьте `-no-open`.

## Как это работает

Клиент отправляет `POST {AI_BASE_URL}/chat/completions` с заголовком
`Authorization: Bearer <AI_API_KEY>` и телом в формате OpenAI Chat Completions.
В потоковом режиме ответ читается как Server-Sent Events: строки `data: {...}`
разбираются, из `choices[].delta.content` собирается текст, `data: [DONE]`
завершает поток. Токены `choices[].delta.reasoning_content`/`reasoning`
(трейс думающей модели) не показываются, но регистрируются как активность,
чтобы не оборвать генерацию.

Веб-интерфейс работает так: браузер шлёт `POST /api/chat` с JSON
`{"message": "...", "format": ..., "maxTokens": ..., "timeout": ...,
"schema": ..., "stop": ...}`, сервер вызывает API и пересылает токены ответа
в тело HTTP-ответа по мере поступления; страница читает поток через
`ReadableStream` и дорисовывает текст в реальном времени. История хранится в
памяти сервера и отдаётся через `GET /api/history`.

Список моделей для сайдбара берётся из `GET {AI_BASE_URL}/models` и
фильтруется по имени (отбрасываются embedding/rerank/whisper/tts/audio/asr).
Если основной endpoint недоступен, используется резервный `[reserve]`, а для
фолбэка списка — `AI_MODELS`/`DefaultModels`.

Диагностика последнего обмена доступна через `GET /api/debug` и возвращает
детали для панели «Детали»: последний запрос, последний ответ, причину
приостановки (ошибка API, «нет ответа», превышение лимита токенов, нарушение
JSON-схемы), а также пошаговый лог `steps` (включая каждый вызов инструмента с
параметрами и результатом), суммарные `tokens`, `prompt_tokens`,
`completion_tokens` и `time_ms`.

## MCP: несколько серверов

MCP-хаб (`mcpclient`, наследие Task17): приложение одновременно
подключено к нескольким удалённым MCP-серверам и мостит их инструменты в
обычный function-calling цикл чата.

### Подключение и конфигурация

- Список серверов — переменная `AI_MCP_URLS` или флаг `-mcp-urls`: пары
  `slug=URL` через запятую. Пусто — список по умолчанию (dubai и
  локальный orbit); значение `off` полностью выключает MCP. Отображаемые имена
  известных slug подставляются автоматически.
- Транспорт — Streamable HTTP официального Go SDK
  (`github.com/modelcontextprotocol/go-sdk`), рукопожатие `initialize` +
  `tools/list` ограничены 15 с. Серверы подключаются **параллельно**; недоступный
  при старте сервер не мешает остальным — в консоль пишется warning, чат
  продолжает работать без его инструментов.
- Таймаут одного вызова инструмента — `AI_MCP_TIMEOUT` (по умолчанию 30 с).

### Маршрутизация вызовов

Модель видит инструменты всех серверов как обычные функции. Когда она их
вызывает, хаб знает, какому серверу принадлежит имя, и проксирует вызов
(`tools/call`), ограниченный таймаутом; результат возвращается модели текстом.
Чип в панели «Шаги» показывает сервер-источник и латентность. Если вызов упал
из-за сброса сессии, хаб один раз переподключается и повторяет запрос.

### Коллизии имён

Одинаковые имена у разных серверов запрещены протоколом function calling, поэтому:
уникальное имя остаётся как есть (`orbit_moon_phase`), а дубликаты
выдаются модели с префиксом slug — `dubai__search_products` и
`orbit__search_products`. Префиксы пересчитываются при каждом
изменении набора подключённых серверов (отключился один — префиксы у общих
имён снимаются).

### Тумблер вкл/выкл и отказоустойчивость

- **Тумблер на карточке сервера** (`POST /api/mcp/toggle`): «выкл» отключает
  сессию и **убирает инструменты сервера из списка, передаваемого модели**,
  фоновое переподключение его не трогает; «вкл» подключает сервер заново.
  Состояние держится в памяти (до перезапуска приложения все включены).
  Неподключённый сервер (упал, dial не прошёл) тоже не передаёт инструменты —
  список модели всегда соответствует живым и включённым серверам.
- **Автопереподключение**: фоновый цикл каждые 60 с пытается подключить каждый
  включённый сервер без сессии; вручную — пиктограмма ⟳ на карточке
  (`POST /api/mcp/reconnect`, пустой slug = переподключить все).
- **Fail-fast**: после неудачного дial-а вызовы к этому серверу 30 с падают
  сразу («подождите или нажмите Переподключить»), не тратя таймаут; ручное
  переподключение и автопереподключение обходят ограничение.
- Сессии закрываются корректно (DELETE /mcp) при выходе — обработчик
  SIGINT/SIGTERM.

### API статуса

| Запрос | Ответ |
|---|---|
| `GET /api/mcp` | `{"servers":[{slug,name,url,enabled,connected,server,version,protocol,count,tools[],error}]}` — статус и инструменты каждого сервера. |
| `POST /api/mcp/reconnect` `{"slug":"dubai"}` | Переподключить один сервер (пустой slug — все); ответ — свежий статус. |
| `POST /api/mcp/toggle` `{"slug":"dubai","enabled":false}` | Включить/выключить сервер; ответ — свежий статус. |

## Инструменты агента (function calling)

Модель в этом чате умеет вызывать локальные инструменты, когда это уместно.
Инструменты описываются как OpenAI-совместимые `tools` в запросе к
`/chat/completions`; когда модель запрашивает вызов, сервер выполняет его
локально (не обращаясь к API) и подставляет результат обратно в диалог, после
чего модель продолжает генерацию. Весь обмен проходит внутри одного ответа —
пользователь видит только итоговый текст.

Доступные инструменты:

| Инструмент | Параметры | Результат |
|---|---|---|
| `get_current_time` | `region` (string) — IANA-таймзона, например `Europe/Moscow` | Текущие дата и время в регионе (`2006-01-02T15:04:05Z07:00 (Europe/Moscow)`). |
| `roll_dice` | — | Случайное целое от 1 до 6 (именно игральный кубик d6), каждое с равной вероятностью. |

К ним в веб-чате, CLI и разовом запросе динамически добавляются инструменты
всех подключённых MCP-серверов (см. «MCP: несколько серверов») — модель
смешивает их в одном диалоге: может узнать время локальным инструментом и тут
же сравнить цены на молоко через Dubai Grocery Prices.

Как это работает:

- `tools/tools.go` описывает инструменты (`Definitions`), исполняет их
  (`Execute`) и крутит цикл вызова (`RunLoop`): пока модель запрашивает
  инструменты, они выполняются и их результат возвращается модели. Число
  раундов ограничено: в интерфейсе — ползунком «Максимальное количество
  циклов» (1–10), вне интерфейса — `maxToolRounds` (6).
- `api/client.go` передаёт `tools` в запросе и умеет собирать фрагментированные
  `tool_calls` из потока (SSE).
- Инструменты доступны и в веб-чате, и в CLI чате (`go run ./app` /
  `go run ./app -cli`), а также в разовом запросе.

Примеры:

```sh
go run ./app "Сколько сейчас времени в Токио?"
go run ./app "Брось кубик"
go run ./app "Найди цены на молоко в магазинах Дубая"               # через MCP Dubai Grocery Prices
go run ./app "Сколько сейчас времени в Дубае? И сравни цены на молоко"  # локальный инструмент + MCP
```

## Цепочки инструментов orbit

К 16 «плоским» инструментам orbit добавлены **7 цепочных**: подбор
благоприятной даты и утренний брифинг города исполняются не одним вызовом,
а последовательностью шагов, где каждый следующий принимает результат
предыдущего.

### Как устроены

| Цепочка | Шаги (по полю `next`) | Что делает |
|---|---|---|
| Подбор даты | `elect_start` → `elect_scan` → `elect_score` → `elect_report` | фиксирует цель/город/окно, собирает транзиты по дням, оценивает и готовит отчёт с топ-датами |
| Брифинг | `brief_start` → `brief_collect` → `brief_compose` | фиксирует город, собирает секции (погода, Луна, транзиты, аффирмация), склеивает markdown-брифинг |

- **Сессии и state-машина.** `elect_start`/`brief_start` создают сессию
  (`election_id` / `brief_id`, TTL **1 час**); каждый шаг принимает
  идентификатор, проверяет статус сессии и возвращает поле `next` с
  именем следующего шага. Вызов шага вне порядка или на неподготовленной
  сессии отклоняется с внятной ошибкой («данные не собраны (статус
  started) — сначала brief_collect»).
- **Аргумент `simulate`** (у каждого шага, описание в схеме): `"error"` —
  шаг вернёт ошибку; `"empty"` — шаг вернёт пустой результат. Служит для
  разборов отказоустойчивости без реальных сбоев.
- **Тесты**: `orbit/chain_test.go` — happy path обеих цепочек, ошибка на
  шаге 2, пустой результат на шаге 1, вызов вне порядка, истечение TTL.

### Правила предсказуемости агента

Задание требует трёх гарантий; они обеспечиваются **двумя слоями**:

1. **Guard'ы на сервере (детерминированно).** Отчёт нельзя получить из
   несобранных данных: `elect_score` на пустом сканировании отвечает
   «кандидатов нет — сканирование вернуло 0 дней», `brief_compose` на
   несобранной сессии — «секции брифинга не собраны». Ошибки называют
   шаг и причину, поэтому «результат, которого нет», через guard'ы не
   проходит даже при недисциплинированном поведении модели.
2. **Системный промпт (поведение модели).** `AI_SYSTEM` в `.env`:
   при ошибке или пустом результате не вызывать следующий шаг цепочки,
   остановиться и сообщить, на каком шаге остановилась цепочка и почему;
   не выдавать результат, которого нет; разрешён один повтор того же
   шага — при повторном сбое остановиться. Проверено прогонами: в
   явных и неявных негативных сценариях модель останавливается, называет
   шаг обрыва и причину, а выдуманных дат/прогнозов не появляется.

Проверить вживую: блоб **«Цепочки»** в веб-интерфейсе (успешные сценарии —
на Владимир; негативы сформулированы неявно, без упоминания `simulate`)
или раннер `bin/chain-demo.py elect|brief|elect_err|brief_err|elect_empty|brief_empty`
(сбрасывает диалог, отправляет сообщение, печатает шаги из `GET /api/debug`).

## Планировщик фоновых задач

**Планировщик** (`scheduler/`) — фоновый процесс внутри агента: горутина,
которая по расписанию отправляет в модель задачи-промпты (полноценный запрос
с инструментами — модель может пользоваться и MCP, и локальными функциями)
и сохраняет последние ответы. Данные хранятся в **SQLite** (`scheduler.db`,
`AI_SCHEDULER_DB`): таблица `jobs` — определения задач со сводкой последнего
запуска, таблица `results` — журнал запусков (последние 20 на задачу).
Журнал переживает перезапуск приложения; при первом старте задачи из старого
файла `scheduler.json` переносятся в базу автоматически.

### Семантика выполнения

Планировщик — часть приложения, поэтому **задачи выполняются только пока
приложение запущено**. Если приложение было выключено в момент запуска —
запуск **пропускается и не навёрстывается**: при старте `next_run`
пересчитывается на ближайший **будущий** момент по расписанию. Наверстать
пропущенный запуск можно вручную — кнопкой «▶» на карточке или
`POST /api/scheduler/run` (запуск «сейчас» не сдвигает расписание).

- Тикер срабатывает раз в 30 с плюс пробуждение при изменениях — задержка
  запуска не превышает тика.
- Одна и та же задача не выполняется параллельно с самой собой; длинный
  запуск ограничен таймаутом (`AI_TIMEOUT`, по умолчанию 5 м).
- Результаты — кольцо на 20 последних (`ok`, `dur_ms`, `answer`, `error`);
  ответы обрезаются до 4000 символов.

### Форматы расписания

| Спецификация | Значение |
|---|---|
| `@every 30m` | Каждые 30 минут (минимум `1m`); поддерживаются `s`/`m`/`h`. |
| `09:00` | Ежедневно в 09:00. |
| `09:00,18:30` | Ежедневно в 09:00 и 18:30. |
| `[пн,ср,пт] 09:00` | По дням недели (рус./англ. имена) в заданное время. |
| `TZ=America/New_York` (поле задачи) | Все времена — в указанной таймзоне (IANA); по умолчанию — локальная. |

### Прямой вызов инструмента (без модели)

По умолчанию задача — промпт: модель сама вызывает нужные инструменты и
оформляет ответ (полноценный агентский ход, расходует токены). Если у задачи
заполнено поле **tool** (или «Инструмент MCP» в форме), планировщик зовёт
указанный MCP-инструмент **напрямую**, минуя модель: результат инструмента
без обработки попадает в журнал запусков — 0 токенов, доли секунды, лимиты
LLM API не тратятся. У инструмента не должно быть обязательных аргументов
(вызов идёт с пустыми). Удобно для лёгких частых задач — `pulse_capture`
раз в минуту, снимки показателей и т.п.

### Веб-интерфейс

Блок **«Планировщик»** в сайдбаре (под блоком «MCP»): карточка на каждую
задачу — индикатор статуса, название, расписание и время следующего запуска,
отметка последнего запуска (✓/✗ + сколько назад), **сворачиваемый список
последних результатов**, тумблер вкл/выкл, кнопка **«▶»** (запустить сейчас),
кнопка **«✕»** (удалить). Кнопка **«+ задача»** открывает форму: имя,
расписание, промпт и необязательный системный промпт. Статус обновляется
автоматически раз в 10 с.

### API

| Запрос | Ответ |
|---|---|
| `GET /api/scheduler` | `{"jobs":[{id,name,prompt,system,schedule,tz,model,enabled,running,next_run,last_run,last_ok,last_error,last_dur_ms}]}` |
| `POST /api/scheduler/add` | Добавить задачу; тело — job (обязательны `name`, `prompt`, валидный `schedule`). |
| `POST /api/scheduler/update` | Изменить задачу по `id` (результаты сохраняются). |
| `POST /api/scheduler/remove` | Удалить задачу: `{"id":"..."}`. |
| `POST /api/scheduler/toggle` | Вкл/выкл: `{"id":"..."}`. |
| `POST /api/scheduler/run` | Запустить сейчас: `{"id":"..."}` (409, если уже выполняется). |
| `GET /api/scheduler/results?id=...` | Последние результаты задачи. |

Ошибки валидации — 400, запуск уже работающей задачи — 409, планировщик
выключен (`-scheduler=false` / `AI_SCHEDULER=0`) — 503 для всех эндпоинтов.

### CLI

```text
/sched                                  # список задач
/sched add Итог дня|@every 1h|Сделай краткий дайджест
/sched run baf4e7c7                     # id можно указывать префиксом
/sched on baf4e7c7 | /sched off baf4e7c7 | /sched del baf4e7c7
```

## Безопасность

- `.env`, `.idea/` и `bin/` уже в `.gitignore` в корне проекта — это правило
  действует для всех папок задач, поэтому секреты и артефакты не попадают в
  репозиторий.
- Не передавайте ключ флагом `-api-key` в общих системах: он остаётся в истории
  shell.
- Приложение не пишет ключ и переписку на диск; детали запроса/ответа хранятся
  только в памяти и отдаются в панель «Детали», сам ключ в них не попадает.
